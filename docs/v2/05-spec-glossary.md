## 1. 目的（なぜ作るか）

v2 のコンテンツは **L3（因果モデル）** で書く。L3 の③「適合の軸」は、毎回ゼロから語ると項目間で言葉がバラつき、タクミの頭の中で**体系**にならない。

そこで、全ての L3 項目が共通で参照する **「5つの基礎変数」を先に独立ページで定義**する。これにより：

- 個別項目（バング・カニンガム・トラベラー…）の③が、同じ語彙で書ける
- タクミは「今日の海」をこの5変数で読むスキルが身につく
- → 個別項目を読むたびにこの5語が**強化される**

> **この企画の本質:** コンテンツの語彙を統一する「辞書の中の辞書」を先に作る。

## 2. 完成イメージ（タクミは何を見るか）

### 動線
1. Reference 一覧 (`/reference`) の上に **「まずこの5語：判断の共通言語」** という小さな入り口
2. クリックで `/reference/glossary` に遷移
3. スマホで縦スクロール、5つの変数が順番に並ぶ
4. 各変数は「**1行サマリー** + **詳細展開**」のアコーディオン式

### 5つの変数（[[02-content-model]] §3 を実装）

| # | 用語 | 1行サマリー |
|---|------|------------|
| 1 | **パワー（過不足）** | 風に対して艇を起こせているか。過剰なら逃がす、不足なら受ける |
| 2 | **ツイスト** | 帆の上下のねじれ。風の上下ムラに合わせる |
| 3 | **ドラフト位置** | 帆が最も膨らむ点の前後位置。スピードか上り角かを決める |
| 4 | **迎角** | 帆が風に対して開く角度。シート・トラベラーで操作 |
| 5 | **海面状態** | 波の有無・大きさ。加速の必要性を変える |

### 各変数の中身（テンプレート）

```
# 【変数名】 例: パワー（過不足）

【1行で】
風に対して艇を起こせているか。過剰なら逃がす方向、不足なら受ける方向に調整する。

【もう少し詳しく】
- 何を見て判断するか（観察ポイント）
  例: ヒール角・ティラーの重さ・リーヘルム/ウェザーヘルムの大きさ
- 「過剰」のときに起きること
  例: 艇が起き上がらない・舵が重い・スピードが落ちる
- 「不足」のときに起きること
  例: 加速できない・前に出ない・波で止まる
- どのコントロールで動かすか（横の入り口）
  → [[バング]] / [[カニンガム]] / [[シート]] / ...

【タクミの判断手順】
1. 今日の海でまず「過剰か不足か」を判定する
2. 過剰なら「逃がす方向」のコントロールを選ぶ
3. 不足なら「受ける方向」のコントロールを選ぶ
```

### モバイル UI イメージ

- 縦スクロールで5つが順に並ぶ（1画面に1変数）
- 上部にアンカーリンク（"パワー｜ツイスト｜…"）でジャンプ
- 各変数の見出しはスクロール時に sticky で残す
- 詳細は折りたたみ。タップで開閉

## 5. 新しく登場する概念・技術

ユーザーが**初めて触れる/まだ腹落ちしていない**可能性のあるトピックを丁寧に説明する。

### 5-1. Next.js の Server Component と Client Component の使い分け

このページは「アコーディオン展開」というインタラクションを含むので、サーバーとクライアントの責任分担を意識する。

| 種類 | 役割 | このページでの使い方 |
|------|------|-------------------|
| Server Component | ビルド時 or リクエスト時にサーバーで HTML を生成。JS をブラウザに送らない（軽い） | `page.tsx` 本体。データを `glossary.ts` から読み込み、5つの変数をレンダリング |
| Client Component | ブラウザで JavaScript が動く。`useState` などのインタラクティブな状態を持てる | `GlossaryAccordion.tsx`。開閉ステートを持つ。ファイル先頭に `"use client";` |

**応用イメージ:**
- 全部 Client にすると、JS バンドルが膨らんでスマホで遅くなる
- 全部 Server にすると、開閉のような「クリックで状態変化」ができない
- → **「動かないところは Server、動くところだけ Client」**が Next.js App Router の基本戦略
- 他の場面: 記事一覧（Server） + いいねボタン（Client）、検索結果（Server） + フィルタUI（Client）

### 5-2. TypeScript の `as const` と `readonly` 配列

`glossary.ts` のデータは「**実行時に変わらない静的データ**」なので、型を厳格に定義する。

```ts
export const GLOSSARY = [
  { id: "power", label: "パワー", ... },
  { id: "twist", label: "ツイスト", ... },
] as const;
```

`as const` を付けると、TypeScript はこの配列を **読み取り専用・各要素のリテラル型** として解釈する。`id` が `"power" | "twist" | ...` の型になり、タイポをコンパイル時に弾ける。

**応用イメージ:**
- ルーティング定数・カテゴリ定数・状態マシンのステート定義
- 「コードで定義した有限の選択肢」を型に持ち上げるときの定番

### 5-3. アクセシビリティ：アコーディオンの ARIA 属性

アコーディオンはスクリーンリーダーや keyboard ユーザーが正しく扱えるように、HTML 標準の `<details>/<summary>` を使うか、`button + aria-expanded` を使う。

- `<details>` ベース: JS なしで動く。今回の用途には**こちらを推奨**
- `button + aria-expanded`: アニメーションを細かく制御したいとき

→ **タクミの「30秒で読める」を守るため、過剰な装飾はせず `<details>` で軽く実装する案を推す。**

**応用イメージ:**
- FAQ、設定パネル、エラー詳細の折りたたみなど。ネイティブ HTML で済むものは JS を増やさないのが鉄則。
