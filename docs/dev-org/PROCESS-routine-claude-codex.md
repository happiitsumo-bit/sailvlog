現状の詰まりは実装力ではなく**受け渡し**にある。今日の実測:

| ブランチ分離したCodexに預けたT-29 | **4日間0コミット**（誰も着手していないことに誰も気づかなかった） |

つまり**実装は速い。止まるのは「誰が次に動くか」が宙に浮く瞬間**である。この設計書はその瞬間を無くすことだけを狙う。

## 2. 完成イメージ

オーナーがやること: **GitHub Issue を立てる（または既存Issueにコメントする）。以上。**

```
タイトル: 反省会で艇の名前がすぐ分からない
本文:     色だけじゃ誰が誰か分からん
ラベル:   from-owner
```

そのあと自動で起きること:

```
Issue（from-owner）
      ↓  Night Shift（毎朝5:40）が拾い、朝レポートの「🛠 dev進捗」に載せる
Team Lead が正本（PRD/ARCH/UI-DESIGN）と突き合わせ、TASKS.md のタスクへ変換
   ・既存の決定と衝突しないか
   ・PRD §5「明示的に入れない」に触れないか
   ・ファイル集合を確定させる（＝誰に投げられるかが決まる）
      ↓
      ├─ Codex   ← 仕様が明確・ファイル集合が確定・見た目を含む
      └─ Claude  ← 正本の解釈・設計判断・契約変更・ネット調査
      ↓
Team Lead が実測検証（自己申告を通さない）
      ↓
dev-orgの監査エージェント（code-reviewer / architect / qa-engineer / ux-reviewer）
      ↓
オーナーへレポート（§5の定型フォーマット）
```

**オーナーが読むのはINBOXに書いた1行と、最後のレポートだけ**になる。

## 3. 実装する機能の一覧

### 3.1 受付口: GitHub Issue（オーナー指示 2026-07-30）

**タスクの状態の正本は GitHub Issue**（`happiitsumo-bit/sailvlog`）。オーナーもここに書く。

- オーナーは**整理せずに書く**。「なんか使いにくい」「ここで迷った」レベルで可（分類はTeam Leadの仕事）。ラベルは `from-owner` だけ付ければよい（付いていなくてもTeam Leadが拾う）
- **⚠ このリポジトリは PUBLIC。Issueは誰でも読める。** 接続文字列・トークン・個人情報・部員の実名は書かない（要望・課題そのものは問題ない）
- 当初案の `docs/dev-org/INBOX.md` は**採用しない**（オーナー指示によりIssueへ統合。受付口を2つ作ると必ず片方が死ぬ）

#### ラベル体系（2026-07-30作成）

| 種別 | ラベル | 意味 |
|---|---|---|
| 重大度 | `blocker` / `major` / `minor` | Gate運用ルールの3段階と同義。緩めてよいのは `minor` のみ |
| 担当レーン | `lane:claude` / `lane:codex` | §3.2の判定基準で振る |
| 領域 | `area:backend` / `area:frontend` / `area:docs` | 並列起動時のファイル集合の目印 |

| 未分類 | `from-owner` | **オーナーが書いた生の要望**。Team Leadが分類する前の状態 |

#### `TASKS.md` との役割分担（二重管理を避ける）

`workspace/CLAUDE.md` の「同じ情報を複製しない」に従い、次のように分ける。

- **Issue = 作業の状態**（open/closed・担当・進捗コメント）。**今後の新規タスクはIssueのみに作る**
- **`TASKS.md` = 設計文書としての分解・依存関係・検証の証拠**。S1/S2の完了記録と長い実測ログはここに残す（履歴として凍結）
- 移行時に**完了済みタスクとバックログ（BL-01/BL-02）はIssueに移していない**（履歴を二重に持たないため）。open だったものだけ移した

### 3.2 分業の判定基準（レイヤーではなくファイル集合で割る）

今日の失敗から確定した基準。**技術レイヤー（フロント/バック）で割ってはいけない。**

| 条件 | 担当 |
|---|---|
| 仕様が明確／触るファイル集合が確定している／見た目・UIを含む | **Codex** |
| 正本の解釈が必要／設計判断（ADR起票相当）／複数ファイルにまたがる契約変更／ネットワーク調査／Gate判定 | **Claude（Team Lead）** |
| 両方の性質を持つ | **投げる前に分割する。**分割できないならClaudeが直列でやる |

**なぜレイヤー分割が失敗したか**: `parallel-dev.md` は「並列にしてよいのは触るファイルが重ならない**独立タスク**だけ」と定めており、単位はタスクである。R-03のように**1つの契約をフロントとバックの両側から実装する**課題をレイヤーで割ると、片側が完成しても必ずもう片側待ちになる（実際にbackendだけ完成して③Gateが4日開かなかった）。

### 3.3 並列起動時の必須チェック

Codexは**worktreeではなく、Team Leadと同じ作業ディレクトリで動く**（§6-①）。分離は仕組みではなく指示で成立している。よって起動前に必ず:

1. 各レーンが触るディレクトリを**明示的に列挙**し、重複ゼロを確認する
2. Codexへのプロンプトに「**触ってはいけないディレクトリ**」を書く
3. 重複があるなら並列にしない（直列にするほうが速い。`parallel-dev.md`の判断どおり）

### 3.4 検証は必ずTeam Leadが実測する

**委譲先の「できました」を報告に流さない。** 今日の実例:

- 実装者は「152 passed」と報告。私が実行して154 passed（私が追加した2件込み）を確認してから採用した
- 実装者が「ADR未規定なので直さず報告」とした穴（最後のadminを降格できる＝チームが管理不能になる）を、私が塞いだ
- Codexは報告を返さなかったが、私が実行して `tsc 0 / vitest 59 passed / build成功` を確認できた

## 6. 未確定・要検証（正直に残す）

### ① Codexはworktree分離されていない

実測したプロセス:

```
node .../openai-codex/codex/1.0.6/scripts/app-server-broker.mjs serve
     --endpoint unix:...broker.sock  --cwd /Users/nova/workspace/dev/sailvlog
codex app-server
```

`--cwd` がリポジトリ直下そのままで、worktreeではない。今回はファイル集合が分かれたので事故らなかったが、**構造としては `parallel-dev.md` が警告している「同居状態」に近い**。将来 `isolation: worktree` 相当の分離を入れるかは、事故が1回起きるまで保留とする（今の規模では分離コストのほうが高いと判断）。

### ② Codexのネットワーク可否 — 前言を訂正する

**訂正**: 前回「Codexはネットワーク無効」と断定したが、**その根拠は誤りだった**。私が引用したのは `/Applications/ChatGPT.app/.../codex sandbox ... network = {enabled = false}` というプロセスで、これは**ChatGPTデスクトップアプリ側の別プロセス**であり、プラグイン経由で起動したCodexタスク（`app-server-broker.mjs`）ではない。別物を根拠にしていた。

**改めて実測できたこと**:

| 条件 | 結果 |
|---|---|
| サンドボックス外で `curl https://example.com` | **HTTP 200** |
| `codex sandbox -- curl https://example.com` | **HTTP 000（到達せず）** |
| `~/.codex/config.toml` の設定 | `sandbox_mode = "workspace-write"`。ネットワーク関連の記述なし |
| CLIから `network.enabled = true` を上書きして有効化 | **3回試して成功せず**（`-c sandbox_workspace_write.network_access=true` は無視、`-P` プロファイル指定は curl が SIGABRT） |

**確定していないこと**: 上の測定は `codex sandbox` サブコマンドに対するもので、**プラグイン経由で走る実際のCodexタスクが同じ制約下にあるかは未検証**。オーナーの「向こうのアプリからだと普通に使える」という観測とも整合しない。

**【確定 2026-07-30・`codex exec` で実測】** オーナー提案の `codex exec` 構成を検証する過程で決着した。

| 実行条件 | 結果 |
|---|---|
| `codex exec --ephemeral --sandbox read-only` | **HTTP 000 / curl exit 6（名前解決不能）** = ネットワーク遮断 |
| `codex exec --ephemeral --sandbox workspace-write -c 'sandbox_workspace_write.network_access=true'` | **HTTP 200** = ネットワーク到達 |

**結論**: デフォルトでは遮断されているが、**呼び出しごとに有効化できる**。よって「Codexはネットワークが使えない」は誤りで、正しくは「**明示的に許可しない限り使えない**」。ネットワーク調査もCodexに投げられる。

**ただし設計上の注意**: 有効化のキーは `sandbox_workspace_write.network_access` で、**`workspace-write` 名前空間に属する**。つまり「`read-only` かつネットワーク有り」は指定できない。ネットワーク調査をさせたい場合は `workspace-write` を渡すことになるので、**書き込み先を捨ててよい空ディレクトリに `-C` で限定する**（`--skip-git-repo-check` 併用）。これによりリポジトリを書けないまま調査だけさせられる。※この回避策自体は**未検証**。

**副産物**: `codex exec` は提案にあった `--ephemeral` / `-s` / `-o` / `--json` / `-C` / `--add-dir` すべて実在。加えて **`--output-schema <FILE>`**（最終応答をJSON Schemaで縛る）があり、機械可読な報告を取るなら `--json` のイベント列より確実。

### ③ ルーチンがINBOXを拾う頻度と実体

「ルーチン」の実体（クラウド定時実行）の設定は本リポジトリ外にあり、本書では**INBOXの形式を決めるところまで**とする。拾う側の設定は別作業。

### ④ 根拠はまだ1回の観測である（自己反論）

「ブランチ分離のCodex＝4日0コミット／サブエージェントのCodex＝35分で完成」という対比は綺麗だが **n=1**。T-29が**仕様の明確なタスクだった**から通った可能性がある。**仕様が曖昧なタスクをCodexに投げたときに何が起きるかは未検証**で、§3.2の判定基準はその前提で「仕様が明確なもの」をCodex側の条件に入れている。

また、**この体制はTeam Lead（私）がボトルネックになるリスクを増やす**。Codexが動かない問題を、私が全部抱える問題に置き換えただけかもしれない。判定材料は「7/31までにT-29とT-30が閉じるか」とし、閉じなければ体制ではなく私の運用を疑う。

## 7. 新しく登場する概念

**`AGENTS.md`**: Codex（および多くのコーディングエージェント）が、リポジトリを開いたときに**自動で読む常設指示ファイル**。Claude Codeの `CLAUDE.md` に相当するもののエージェント共通版。人間向けの `README.md` とは役割が違い、「エージェントが破ってはいけない約束」を書く場所。プロンプトに毎回書く必要がなくなるのが利点で、逆に**ここに書き忘れた制約は守られない**。

**permission profile（Codex）**: Codexが実行するコマンドに与える権限のセット（どのディレクトリに書けるか・ネットワークに出られるか）。`~/.codex/config.toml` の `permissions.<名前>` で定義し、`-P <名前>` で適用する。§6-②で触っているのがこれ。
