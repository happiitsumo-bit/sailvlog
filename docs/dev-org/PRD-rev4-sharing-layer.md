## 0. まず正直に — rev.3 は何を間違え、何を間違えていないか

**間違えた点（Team Lead分析に同意）**: オーナーの当初要求は「全国の一般セーラー＋自部の部員」だった。rev.3 §3 はこれを「Phase 2 = 他大学の部へのツール導入」に置き換えた。「ツールを他チームにも売る」と「知見を全国のセーラーに届ける」は別物であり、後者が要求だった。これはターゲットの矮小化であり、rev.4 で正面から扱う。

**間違えていない点（迎合しないために明記）**: rev.3 が共有機能を外したのは見落としではなく、v1 失敗診断（PRD §0「ブログ・Q&A・フィードの寄せ集め → 第三者が使う未来が見えない」）に基づく意図的な絞り込みだった。**共有機能を「先に」作ると空の箱で死ぬ、という v1 の教訓自体は今も正しい**。したがって rev.4 の論点は「共有層を足すか否か」ではなく、**「v1 と同じ死に方をしない共有層の形式と投入順序は何か」**である。

**Team Lead 仮説の採否**: 「v1 の失敗は形式でなく『ゼロから書く空の箱』だったから。今回はリプレイ・注釈という練習の副産物が供給源にあり、『公開昇格させる場』なら回避できる」— この仮説を**条件付きで採用**する。根拠は §2 の国内実例。ただし仮説への反論（生の注釈は公開に耐えない等）は実在する弱点であり、§4 の推奨案に「昇格時の軽い編集ステップ」として対策を組み込み、§6 で安い検証を義務化する。

## 1. 供給源仮説の外部根拠 — 「記録の副産物が公開コンテンツになる」国内実例

- **YAMAP（登山）**: 登山中のGPS収録がそのまま「活動日記」として公開され、他のユーザーがその軌跡をダウンロードして自分の登山計画に使う（[ヘルプ: 他のユーザーの軌跡を見る/DL](https://help.yamap.com/hc/ja/articles/900000928823)、[活動日記](https://yamap.com/activities)、[別サービスのGPX取込も可](https://help.yamap.com/hc/ja/articles/900000967783)）。**「自分のための記録」が追加執筆ほぼゼロで「他人の計画の材料」になる**構造で国内最大級の登山コミュニティが成立している。sailvlog の「セッション（航跡＋注釈）を公開昇格 → 他部のセーラーがコース判断の材料に読む」はこの相似形
- **Strava（ラン/自転車・世界）**: 同型（計測の副産物＝公開アクティビティ）。汎用性の傍証
- **アングラーズ（釣り・rev.3 §2 既出）**: 構造化カード（釣果記録）の公開で国内最大級。案A（カード）の公開昇格にも同型の前例がある

**含意**: 「書かせる」のではなく「録れたものを公開する」モデルは、日本語圏ニッチスポーツで実証済み。v1 の Article/Q&A/フィードにはこの供給源がなかった。**ただし** YAMAP/Strava は「個人の記録を個人が公開する」モデルであり、sailvlog の一次データは「部の反省会の議論ログ」= 集団の内輪データである点が異なる。この差が §4 の自己反論の核になる。

## 3. 推奨 — (iv) ハイブリッド段階案（核は (iii) 公開昇格型）

**一言で**: 共有層は「新たに書かせる場」ではなく「Phase 1 の運用ループで生まれたセッションを、部内 → 限定公開 → 全国公開へ昇格させるレール」として作る。段階は次の3つで、各段階に前進条件（計測値）を置く。

| 段階 | 内容 | 前進条件（これを満たすまで次を作らない） |
|---|---|---|
| **共有0（0円検証・実装なし）** | Phase 1 中に、反省会済みセッション1〜2本を**手動で**「公開に耐える形」（スクショ/画面録画＋学び要約）に編集し、X・note 等へ投稿。全国のセーラーが読むか・反応するかを先に計測 | — （Phase 1 と並走。実装ゼロ・0円） |
| **共有1（限定公開URL）** | セッション単位の公開範囲: 部内（デフォルト）/ リンクを知っている人。昇格時に「学びの要約」1件を必須入力。注釈は昇格時に**公開する注釈を選ぶ**（デフォルト非公開＝恥の文化への対策） | Phase 1 成功指標①〜③達成（供給の実証）＋共有0で外部反応が1件以上 |
| **共有2（公開ギャラリー）** | 全国公開セッションの一覧ページ（艇種・風速・会場で引ける）。無認証閲覧。OGP でSNS共有時に航跡サムネイル表示 | 共有1で昇格セッションが月2本以上×2ヶ月、かつ部外閲覧が発生している |

**この設計が v1 の失敗構造を回避する理屈**（3点、すべて計測で裏どり予定）:
1. **供給**: 共有層は自前の執筆を要求しない。Phase 1 が成功していれば公開候補（セッション＋注釈）は毎週自動的に増えている。Phase 1 が失敗していれば共有層は作らない — 空の箱を作らない構造的保証
2. **需要**: 「作ってから来るか確かめる」でなく「作る前に共有0で確かめる」。手動投稿への反応ゼロなら共有1以降は NO-GO
3. **文化（恥）**: 生の注釈の全公開を強制しない。昇格時の選別＋要約添付で「見せられる形」への編集コストを最小化する

### 推奨への自己反論（説得耐性）

1. **「内輪の反省会ログは、選別しても第三者に読めない」可能性**。YAMAP の活動日記は個人の完結した記録だが、sailvlog の注釈は「4423 ここでタック遅い」のような文脈依存の断片。要約1件を足しても、他部のセーラーには意味不明かもしれない。→ だからこそ共有0（手動検証）を実装より前に置いた。ここで「読めない」と判明したら、共有層は要約でなく**記事寄り（(iv)第3段階の前倒し）**へ形式を変える必要があり、実装増分の見積りは崩れる
2. **恥・戦術秘匿の文化で昇格が起きない**可能性。レース戦術は競争資源であり、インカレで当たる相手に手の内を見せる動機がない。昇格数ゼロなら共有層は死ぬ。→ 対策は「練習セッションのみ昇格・レースは非公開」等の運用だが、練習の航跡に全国のセーラーが読む価値が残るかは未検証。共有0で「練習ネタの反応」を必ず1本は試す
3. **「届く導線がない」問題は解決していない**。(iii) は発見性を X 等の既存SNSに外注する設計であり、部活アカウントのフォロワー数次第では「全国」に届かず「知り合いの数十人」で終わる。これは失敗ではなく現実的な初期値と捉えるが、オーナーの「全国」の期待値とはギャップがあり得る。ここは Gate で目線合わせしたい
4. **product-lead 自身の一貫性への疑い**: 私は rev.3 で共有を Phase 2 に送った。今回オーナー指摘を受けて共有層を足す案を書いている — 「オーナーの発言で変わっただけ」ではないか? 変わった証拠は2点: ①当初要求のターゲット定義を私が取り違えていた事実の確認 ②供給源仮説の外部根拠（YAMAP）の確認。ただし**「MVPには入れない」という順序判断は rev.3 から変えていない**（§5）。ここが迎合との分水嶺だと自己認識している

### ADR-005（Post/PostLike/Follow 削除）への影響裁定

- **(ii) を却下する本推奨では、削除方針は維持**（BL-01 のまま）。再裁定は不要

- ADR-003（Article 凍結・削除予定なし）は本推奨で**正しさが追認される**（(iv)第3段階での限定復活余地）。変更不要

## 5. 実装タイミングの提案

**結論: MVP には入れない。共有0 のみ Phase 1 と並走し、共有1 は Phase 1 成功指標達成後（≒PRD の Phase 2）に着手する。**

- **今〜B-1 判定（2週間）**: 何も変えない（前提条件）。本ドラフトのオーナー承認のみ進める
- **Phase 1（MVP 8週間）**: 実装スコープ不変。追加は2つだけ — ①共有0 の手動検証（実装ゼロ） ②architect への要件伝達（§4。設計の手戻り防止であり実装ではない）
- **Phase 2**: 共有1 を A接続と並ぶ Phase 2 の柱に昇格。共有0 の結果が悪ければここで形式変更 or 断念を判断
- **MVP に入れない理由**（オーナー意向「今の機能は残す＋その上に追加」とは両立する。「追加のタイミング」だけの議論）: ①公開する中身は Phase 1 の成功そのものであり、順序を入れ替えると v1 の再演になる ②MVP は既に Architecture Gate 通過済みで、スコープ追加は 8週間の検証設計を壊す ③共有0 が実装なしで需要を測れる以上、先に作る理由がない（計測より先に対策をしない）

**面接価値の観点（1回だけ）**: 「クローズドな実用ツールで供給を実証してから公開コミュニティへ段階昇格する」は、v1 の失敗診断 → rev.3 の絞り込み → rev.4 の段階解放という一貫したプロダクト戦略の物語として語れる。機能を足したことではなく**足すのを遅らせた判断**が語りの核になる。

## 7. Product Gate 再判定用サマリー

1. **オーナー指摘は正当**（当初要求「全国の一般セーラー」を rev.3 が「他大学へのツール導入」に矮小化）。ただし共有を MVP から外した順序判断自体は v1 の教訓どおりで、今回も**「上に足す」を「先に足す」にしないこと**が生死を分ける。
