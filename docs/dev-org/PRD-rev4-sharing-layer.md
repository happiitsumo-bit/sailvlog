## 0. まず正直に — 何が変わり、何を変えないか

**オーナー裁定で変わったこと**: rev.4 は「公開昇格のみ・フォローなし・アカウントは既存User/Teamのまま」を推奨し、X型（投稿＋フォロー）を却下した。オーナーはこれを部分的に覆した: **スタンドアロン投稿・フォロー・団体アカウントを製品ビジョンに含める**。これはプロダクトの最終形を決めるオーナーの価値判断であり、最終判断は人間が下すという原則どおり**境界条件として受け入れる**。

**product-lead として変えないこと（迎合との分水嶺）**: 私のリスク評価自体は変わっていない — 評価を変える新しい証拠が出ていないからだ。「供給源なき投稿箱＋小さい母集団のフォローグラフ」は v1 が死んだ構造そのものであり、この危険は裁定後も消えない。したがって本改訂の仕事は「SNS 層をやるか」の再論ではなく、**「オーナーが決めた最終形へ、v1 と同じ死に方をせずに到達する順序と緩和策を設計する」**ことである。緩和してもなお残るリスクは §3 に残ると明記する。

**rev.4 から生き残る資産**: 供給源仮説（YAMAP 型「記録の副産物が公開コンテンツになる」— [他ユーザー軌跡のDL](https://help.yamap.com/hc/ja/articles/900000928823)・[活動日記](https://yamap.com/activities)）、共有0（実装ゼロの手動需要検証）、「各段階の前に前段が回った証拠を要求する」段階設計。これらは SNS 層を成立させるための呼び水・計測装置としてそのまま使う。

## 1. 共有層の最終形（オーナー裁定の要件化）

| # | 裁定 | 要件としての解釈 |
|---|---|---|
| 1 | ゼロから作る投稿も認める | リプレイに紐づかないコンテンツ（投稿）を作成・公開できる。ただし**自由記述の空箱にはしない**（§3 の構造化テンプレが成立条件） |
| 2 | public / followers-only / private の3層可視性 | コンテンツ単位で公開範囲を選択。followers-only はフォロワーのみ閲覧可 |
| 3 | 個人と団体の両アカウント | 部・団体名義のアカウントを作成でき、個人・団体どちらもフォロー/被フォローの主体になれる |

**裁定が触れていない論点を2つ、Gate で確認したい**（差し戻しではなく、3層モデルに収まらない実在の穴）:

- **(論点1) 「部内限定」は3層のどれでもない。** 現行 MVP の中核可視性は「Team メンバーのみ」（ARCH §4: 全 session ルートで TeamMember 検証）。部員 ≠ 団体アカウントのフォロワー（フォローは誰でもできるが、部員は名簿=TeamMemberで管理される）。反省会の生データを followers-only にすると**部外のフォロワー全員に見える**ため代替にならない。→ 提案: 可視性は実質4値 **public / followers / team(部内) / private** とし、UI 上「チーム内共有」は団体アカウント配下の第4の選択肢として見せる。3層に無理に畳むと MVP の「部内限定」が壊れる
- **(論点2) followers-only は初期にはほぼ private と等価。** フォロワー数が一桁の期間、followers-only コンテンツの実効読者はゼロに近い。機能は作るが、価値が出るのはフォローグラフが育った後 — だから §2 の段階で最後に置く

## 2. 段階の再構成（どの段階で何が入るか）

rev.4 の「共有0→1→2」を、オーナーの最終形（SNS層）まで含めて4段に再構成する。**各段の着手条件は前段の計測値**（空の箱を作らない構造的保証は維持）。

| 段階 | 入るもの | 入らないもの | 着手条件（前進条件） |
|---|---|---|---|
| **共有0（0円検証・実装なし）** | 反省会済みセッション1〜2本＋セッティングカード1〜2枚を手動編集して X/note へ投稿。「全国のセーラーが読むか・どの型に反応するか」を計測 | 一切の実装 | なし（Phase 1 と並走） |
| **共有1: 公開昇格＋限定公開URL** | セッション単位の可視性（team デフォルト → リンク限定 / public へ昇格）。昇格時「学びの要約」必須・注釈は選別公開。OGP | アカウント・フォロー・スタンドアロン投稿 | Phase 1 成功指標①〜③（供給の実証）＋共有0で外部反応1件以上 |
| **共有2: アカウント基盤＋構造化投稿** | 個人プロフィール・**団体アカウント**（部のショーケース: 公開セッション・投稿・所属が並ぶ）。スタンドアロン投稿を**構造化テンプレ2種に限定**して解禁: (a) セッティングカード（rev.1 A案の再接続。艇種×風速×設定値＋写真） (b) 練習/レース振り返り（リプレイ添付は任意=ゼロから作成可）。可視性 public/team/private | フォロー・フィード・自由記述ブログ | 共有1で昇格が月2本以上×2ヶ月＋部外閲覧の発生 |
| **共有3: フォローとフィード** | アカウント単位フォロー・followers-only 可視性の実効化・フォロー中フィード（時系列のみ）。投稿種別の追加検討（自由記事はここで再判定） | いいね/ランキング等のゲーミフィケーション（「文化が先」の原則維持）・推薦アルゴリズム・DM | 共有2で部外アカウント登録10件以上＋自部以外からの投稿発生 |

**この並びの理屈**: ①中身（公開昇格されたリプレイ・カード）が先、器（プロフィール・フィード）が後 ②団体アカウントをフォローより先に置くのは、**大学の部には「部として発信する既存動機」（新歓広報・OB/スポンサー向け・成績報告）が実在**し、個人の投稿動機より供給が堅いから。団体ページは「フォロワーゼロでも意味がある」（URL を新歓ビラ・部の X に貼れる）のに対し、フォロー機能はグラフが育つまで無価値 — 前提の少ない順に作る。

## 3. 「空の箱」リスクへの対処（緩和策と、それでも残るリスク）

**緩和策（採用3つ）**:

1. **投稿に型を用意する（自由記述を最後まで解禁しない）**: 共有2の投稿は「セッティングカード」「振り返り」の2テンプレのみ。書くことが決まっているフォームは白紙エディタより供給障壁が桁違いに低い（アングラーズの釣果カードで国内実証済み・PRD rev.3 §2）。**rev.1 の A案（カード図鑑）がここで再接続する** — B-1 並行検証の A検証（Google フォーム運用）の結果が、そのまま共有2のカード型の需要証拠として流用できる。主役選定で A が負けても A の資産は共有層で回収される
2. **副産物投稿を呼び水にする**: 共有2 時点でフィードはまだ無いが、団体ページ・公開一覧の初期在庫は共有1 の昇格セッションが埋める。「空のプラットフォームへ最初の投稿をする心理障壁」を、既に存在する公開リプレイが吸収する
3. **初期は投稿種別と可視性を絞る**: 種別2つ・followers-only は共有3まで封印。選択肢を減らすことが「何を投稿する場か」の輪郭を作る（v1 は Article/Q&A/Post が並列で輪郭がなかった）

**それでも残るリスク（消えないと明記する）**:

- **R-a: 自部以外の供給が発生しない。** 緩和策はすべて「自部の供給」を保証するだけ。全国のセーラーが「読む」から「書く」に転じる保証はどこにもない。共有3の着手条件（自部以外からの投稿発生）を満たせず、共有2止まり＝「自部のショーケース＋公開アーカイブ」で終わる可能性は**高い**。ただしその終着点でも「部内ツール＋部の公開広報」として実用価値は残る（v1 との違い: 共有層が死んでも部内層は生きている）
- **R-b: フォローグラフが臨界質量に届かない。** 国内学連セーラー人口は小さい（rev.3 §2）。共有3を作っても followers-only とフィードが「誰もいない SNS」になる確率は構造的に高い。着手条件（部外10アカウント）で「作る前に」検知する設計だが、条件を満たしても過疎の可能性は残る
- **R-c: 戦術秘匿・恥の文化で昇格も投稿も起きない**（rev.4 から継続）。共有0 で最初に計測する
- **R-d: スコープ膨張。** アカウント・フォロー・可視性4値は、E2 リプレイ本体より大きい開発物になり得る。学生1人の開発リソースで「リプレイの磨き込み」と「SNS 層」は食い合う。段階の着手条件はこの防波堤でもある

## 4. 推奨への自己反論（説得耐性）

1. **「段階案は SNS 層の体のいい先送りではないか」** — オーナーは最終形を示したのに、共有3（フォロー）は最短でも数ヶ月先になる。オーナーの時間軸（在学期間・就活）と合わない可能性がある。→ 反駁: 順序を縮めて器から作れば v1 の再演で、面接で語れるのは「同じ失敗を二度した話」になる。ただし**時間軸の優先順位はオーナーの判断事項**なので、§8 の判定選択肢に「共有2の前倒し」を残した
2. **「構造化テンプレが効く証拠は自プロダクトでは未検証」** — アングラーズ/YAMAP は前例であって証明ではない。カード型が自部で回るかは B-1 の A検証を見るまで不明。A検証が惨敗した場合、共有2 のテンプレ戦略は主柱を失い、共有層の再設計が要る
3. **「団体アカウント先行は広報 SNS 化の入口」** — 部の新歓広報が主用途化すると「知の共有」から「かっこいい航跡を見せる Instagram」へドリフトする恐れ。成功指標を「昇格数・学び要約の記入率」に置き、閲覧数・フォロワー数を KPI にしない（§7）ことで牽制するが、完全には防げない
4. **product-lead 自身の一貫性**: rev.4 で却下した X 型要素を rev.4.1 で組み込んだのは「オーナーの発言で変わった」のではないか? — 事実として方針転換の起点はオーナー裁定であり、新しい証拠で私の評価が変わったのではない。だからこそ本ドラフトは「評価は変えず、リスクを残存として明記した上で、到達順序を設計する」構成にした。R-a〜R-d を承知で進む判断はオーナーに帰属する

## 5. データモデルへの含意（architect への要件。実装・技術裁定はしない）

### 5-1. 「団体アカウント」と既存 User/Team の関係 — 2案の論点整理（裁定は architect）

| 観点 | **案X: Team を団体アカウントに昇格** | **案Y: Account 抽象を新設**（Account は User または Team と1:1、kind=user\|org） |
|---|---|---|
| 概念の整合 | Team は現在「部内作業空間」（TeamMember・部内限定 API の主体）。公開プロフィールという別役割が同居 → 1モデル2責務 | 「作業空間(Team)」と「公開上の人格(Account)」を分離。Team は無変更で、公開面だけ Account が担う |
| 既存互換 | ◎ Session.teamId・TeamMember 検証・部内限定 API は無変更。Team に公開プロフィール列を足すだけ | ○ 既存モデルは無変更だが、公開コンテンツの author 参照を Account に寄せる横断変更が入る |
| フォローの表現 | User→User と User→Team の2種が必要（多態 or 2テーブル。v1 Follow は User→User のみで形が合わない） | Follow は Account→Account の1種で閉じる（個人/団体は kind の差） |
| 将来の拡張 | 「Team 機能を使わない団体」（学連・ショップ・OB会等）が表現できない | kind 追加で表現可能 |
| 移行コスト | 小 | 中〜大（認可・author 参照の変更範囲次第） |

**product-lead からの要件**（どちらの案でも満たすこと）:
1. 現行 MVP の「部内限定」保証（TeamMember 検証）を一切弱めない
2. 「team（部内）」の可視性を独立した第4の値として保存する（§1 論点1。followers への読み替え禁止）
3. **Follow の実装は共有3まで遅延できる設計にする**（アカウント基盤とフォローを密結合させない）
4. v1 Follow（User→User）スキーマの再利用可否はこの裁定に従属する（§6 の ADR-005 再裁定とセット）

### 5-2. MVP 中に入れるべき先行下地（後から変えると高くつくもの）

B-1 検証中（2週間）は不変。**S1 着手時**に architect が以下を裁定することを要件化する。判断基準は「今なら列1本・後からだと全行移行＋認可書き換え」級か否か。**空テーブルの予約はしない**（使われないスキーマは負債・YAGNI 違反。coordinator 例示の「Follow/Account のスキーマ予約」はこの理由で不採用とし、代わりに「後付け可能な形の確認」に置き換える）:

- [ ] **visibility 列を Session に最初から持たせる**（値は当面 `team` 固定でよい。値集合の設計だけ4値 public/followers/team/private を見込む）。後付けは全行 UPDATE＋全ルートの認可条件変更になる
- [ ] **公開 URL の識別子**: Session id は連番 Int（ARCH §3）。公開時に連番 URL は列挙で非公開境界の穴になりやすい。公開用の推測不能スラッグ（列 or 生成規則）の設計余地を今のうちに確保
- [ ] **Annotation の公開制御の概念**（昇格時の選別公開）。列を今切るかは architect 判断、概念だけ要件として確定
- [ ] **author 参照の将来互換**: 新規モデル（Session/Track/Annotation）の作者参照が、案Y（Account 抽象）に後から付け替え可能な形かの確認
- [ ] **Follow/Account テーブルの新設は今はしない**（共有2/3 着手時）

## 6. ADR-005（Post/PostLike/Follow 削除）への影響 — 再裁定が必要

rev.4 では「X型却下につき削除方針維持」としたが、**オーナー裁定でフォローが最終形に入り、前提が崩れた**。再裁定の提案:

- **BL-01（物理削除）のうち Follow を「保留」に変更**。実施条件を「Phase 1 安定後＋オーナー承認」から「**共有3（フォロー）の設計確定後**＋オーナー承認」に差し替え。v1 Follow（User→User）が案X/案Y のどちらで再利用・作り直しになるか確定するまでスキーマ残置（凍結・410）を継続 — ADR-005 自身の根拠である可逆性の論理をそのまま適用
- **Post/PostLike は削除方針を維持してよい**（共有2 の投稿は構造化テンプレで、v1 Post の自由短文とはモデルが別物になる公算大）。ただし物理削除の実施は Follow と同じバッチに寄せるのが安全
- ADR-003（Article 凍結・削除予定なし）: 変更不要。自由記事は共有3 で再判定のため、凍結維持が引き続き正しい

## 7. MVP スコープへの影響判定と成功指標

**判定: 現行 MVP（E2 リプレイ・部内限定）は変えずに維持できる。** SNS 層で MVP に食い込むのは §5-2 の先行下地（設計判断＋列1〜2本級）のみ。B-1 並行検証（2週間）は一切変更しない。

- **今〜B-1 判定**: 何も変えない。本ドラフトの承認のみ進める
- **Phase 1（MVP）**: スコープ不変＋共有0 並走＋§5-2 の下地裁定を architect へ
- **Phase 2**: 共有1（公開昇格）＋A接続（rev.3 どおり）
- **Phase 3**: 共有2（アカウント基盤＋構造化投稿2種）
- **Phase 4**: 共有3（フォロー・フィード）

**成功指標の追加案（PRD §6 へ）**:
- 共有0: 手動公開投稿（リプレイ2本＋カード2枚）で部外セーラーの反応合計1件以上・**型別の反応差**を記録（共有2のテンプレ選定の証拠になる）
- 共有1: 昇格セッション月2本以上・学び要約の記入率100%
- 共有2: 団体ページ公開＋構造化投稿が月4件以上（自部）＋部外ユニーク閲覧の発生
- 共有3着手条件: 部外アカウント登録10件以上＋自部以外からの投稿発生
- **非KPI の明記**: 閲覧数・フォロワー数は着手条件にのみ使い、成功指標にしない（広報SNS化ドリフトの牽制・§4 反論3）

**面接価値の観点（1回だけ）**: 「オーナー要求の最終形（SNS）を否定せず、失敗履歴（v1）から逆算して各層に計測ゲートを置いた段階的リリース設計」は、機能の話でなく**リスク管理と順序の意思決定**として語れる。可視性4値の発見（部員≠フォロワー）も、要件の穴を仕様化前に見つけた実例になる。

## 8. Product Gate 再判定用サマリー（rev.4.1）

1. **オーナー裁定3点（ゼロから投稿・3層可視性・個人/団体アカウント）をすべて組み込んだ**。到達順序は4段: 共有0（手動検証・0円）→ 共有1（公開昇格）→ 共有2（団体アカウント＋構造化投稿2種: セッティングカード/振り返り = A案の再接続）→ 共有3（フォロー・フィード）。各段の着手は前段の計測値が条件 — 「器より中身が先」の防波堤は維持。
2. **確認したい論点が1つ**: 「部内限定」は public/followers/private の3層に収まらない（部員≠フォロワー。反省会の生データが部外フォロワーに見えてしまう）。可視性を実質4値（＋team）とする前提でよいか。
3. **残存リスクを承知で進む判断になる**: 自部以外の供給が発生せず共有2止まりの可能性は高い（それでも部内ツール＋部の公開ショーケースとして生存）。フォロー層は母集団の小ささゆえ過疎リスクが構造的に残る。緩和（テンプレ・呼び水・種別絞り）はしたが消えてはいない。
4. **MVP（E2 リプレイ・部内限定）は不変で維持可能**。食い込みは先行下地のみ（visibility 列・公開スラッグ・注釈公開制御の概念・author 参照の将来互換 — S1 着手時に architect 裁定）。**ADR-005 は再裁定が必要**: Follow の物理削除を「共有3 設計確定後」まで保留に変更提案（Post/PostLike の削除方針は維持）。
5. **判定依頼**: (a) 本4段案でGO（MVP不変・下地のみ先行・可視性4値前提） / (b) 共有2（アカウント＋投稿）を Phase 2 へ前倒し（リプレイ磨き込みとのリソース食い合い R-d を受容する判断として） / (c) 可視性4値の扱い等、論点差し戻しで再提出 / (d) 共有層見送り。

## オーナー裁定追記（2026-07-24・Team Lead記録）— 可視性モデルの簡略化

§5の「4値可視性（public/followers/team/private）」論点にオーナーが回答:「4値はめんどくさい。個人アカウントに属性をつけ、チームに所属している、とすればいいのでは」

**裁定されたモデル**:
- アカウントは個人のみ。チーム所属は個人の属性（現行User+TeamMemberと一致）。チームはエンティティ（ページ）として存在するが、ログインの主体ではない
- 可視性は「所有文脈×シンプル3択」: チーム空間のコンテンツ=所属メンバーが閲覧（構造の帰結、選択肢でない）／個人投稿のみ public / followers / private の3択／チーム→外は「公開昇格」の1方向操作
- 効果: followers-onlyによる反省会生データの部外漏洩経路が構造的に消える。§5の案X/案Y比較はこの裁定を前提にarchitectが再解釈する（現行スキーマとの互換性が高く、手戻りなしの見込み）
