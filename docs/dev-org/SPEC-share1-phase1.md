## 0. この文書が決めること

オーナー裁定（2026-07-25）により、**共有1（公開昇格＋限定公開URL＋OGP）をPhase 2から Phase 1 の最後尾へ前倒しする**。本書はその範囲・作らないもの・データモデル・API・画面・タスク・リスクを確定し、実装GOの判断材料にする。

**前提の変更点を明示する（重要）**: PRD rev.5 §6 では共有1の着手条件を「Phase 1 成功指標①〜③達成＋共有0で外部反応1件以上」としていた。B案はこの**ゲートを意図的に1段飛ばす**判断であり、根拠は「共有0（手動でX/noteに投稿）では、反応が投稿文の巧拙によるものかプロダクトによるものか切り分けられず、計測として弱い」こと。ゲート方式の例外である事実を記録として残す（§7でリスクを明記）。

---

## 1. 目的 — なぜ今これを作るか

| 目的 | 内容 |
|---|---|
| ①計測の質を上げる | 「リプレイそのものが部外に届いたか」をURL単位で観測できる。共有0（手動投稿）では観測できなかった量 |
| ②他大学デモの実弾になる | PRD §6 の Phase 2 着手条件「他大学1チームへ反省会デモ」に、口頭説明でなく**その場で開けるURL**で臨める |
| ③ポートフォリオ価値 | 採用担当・面接官に見せられる公開URLが1本できる。ログインの壁の向こうにある成果物は評価されにくい |
| ④共有2以降の下地 | 可視性モデル（PRD rev.4の裁定）を、机上でなく実装で1回通す。共有2/3の設計リスクが減る |

**この4つに共通するのは「外に出す」ことであり、「SNSを作る」ことではない。** フォロー・フィード・いいねは本スコープに一切含まない（§3）。

## 2. 完成イメージ — ユーザーが何を見て何ができるようになるか

### 2.1 昇格する側（部内・uploader本人 or Team admin）

1. 反省会が終わったリプレイ画面の右上に「**公開する**」ボタンが出る（一般部員には出ない）
2. 押すと昇格ダイアログが開く。ここで3つを決める
   - **学びの要約**（必須・目安200字）— 「この練習で何が分かったか」。部外の人が最初に読む本文
   - **公開する注釈を選ぶ** — 反省会の注釈は**既定で全部非公開**。チェックした注釈だけが外から見える
   - **公開範囲** — 「リンクを知っている人だけ（unlisted）」/「だれでも（public）」の2択
3. 「公開する」で確定 → 推測不能なURL（例 `https://…/p/8Jq2xNbF4tKa`）が発行され、コピーされる
4. リプレイ画面・セッション一覧に「公開中」バッジが付く。取り消しも可能（§5-3で挙動を規定）

### 2.2 見る側（部外・ログイン不要）

URLを開くと、**ログインなしで**次が見える。

```
┌───────────────────────────────────────────────┐
│ sailvlog                          [これは何?] │
├───────────────────────────────────────────────┤
│ 江の島 定期練習 2026-07-20 ・ ○○大学ヨット部   │
│ ┌─ 学びの要約 ────────────────────────────┐ │
│ │ 上マーク回航後の展開が遅れる原因は、下り     │ │
│ │ に入る前のスピン準備タイミングだった。…      │ │
│ └───────────────────────────────────────┘ │
├───────────────────────────────────────────────┤
│         Canvas（ダーク海図面・航跡再生）        │
│         ※ 部内版と同じ再生エンジン              │
├───────────────────────────────────────────────┤
│ [▶] 速さ[1x][4x][8x]   00:14:02 / 02:03:11    │
│ ─●━━━━◆━━━━━━◆━━━━●─  （公開注釈のみピン表示）│
├───────────────────────────────────────────────┤
│ 公開されたメモ                                  │
│  00:14:02 ここのタックが早すぎた               │
├───────────────────────────────────────────────┤
│ sailvlog は大学ヨット部の反省会ツールです（説明）│
└───────────────────────────────────────────────┘
```

- **読むだけ**。書き込み・編集・ログイン導線の強制はない
- SNSに貼るとカード（OGP）が展開され、タイトル・学びの要約・サムネイルが出る

### 2.3 何が「できない」ままか

部外の人はアカウントを作れない（作る画面は出さない）、フォローできない、コメントできない、他の公開セッションを一覧・検索できない。**入口はURL1本だけ**。

## 3. 実装する機能の一覧

### 3.1 作るもの

| # | 機能 | 内容 |
|---|---|---|
| F-1 | 公開昇格 | Session の可視性を `team` → `unlisted` / `public` へ昇格。実行権限は uploader本人 or Team admin |
| F-2 | 学びの要約 | 昇格時に必須入力（1〜400字）。公開ビューの主役テキスト。未入力なら昇格できない |
| F-3 | 注釈の選別公開 | Annotation ごとの公開フラグ。**既定=非公開**。昇格ダイアログでチェックしたものだけ公開 |
| F-4 | 限定公開URL | 推測不能スラッグ（後述）で `/p/[slug]` を発行。`unlisted` は検索避け（`noindex`）、`public` は検索可 |
| F-5 | 公開ビュー | 認証不要の読み取り専用リプレイ。部内版と同じ再生エンジンを再利用 |
| F-6 | OGP | タイトル・学びの要約冒頭・サムネイル画像をメタタグで出力。SNS/LINEでカード展開される |
| F-7 | 公開の取り消し | 昇格を戻す操作。実行後URLは404になる（§5-3） |
| F-8 | 公開状態の可視化 | セッション一覧・リプレイ画面に「公開中/リンク限定」バッジ |

### 3.2 明示的に作らないもの（スコープ膨張の防波堤）

PRD §5「明示的に入れない」の精神をこの機能でも維持する。

- **アカウント登録・ログイン導線の強制** — 公開ビューは完全匿名で読める。「登録して続きを見る」は作らない
- **フォロー・フィード・いいね・公開側コメント** — 共有3（Phase 4）の範囲。ここで作ると v1 の「供給源なき投稿箱」の再演になる
- **公開セッションの一覧ページ・検索・タグ** — 共有2（チームページ）の範囲。入口はURL1本に限定する
- **チームページ・個人プロフィール** — 共有2の範囲
- **閲覧数の表示（UI）** — PRD §5-7 の非KPI原則に従い、数値はDBに持つが画面には出さない（共有2への着手判定にのみ使う）
- **動的OG画像生成** — MVPは静的画像1枚＋動的テキスト。セッションごとの航跡画像生成はバックログ

## 4. データモデルの変更（Prisma・純追加のみ）

ARCH.md §3 の原則「既存モデルは変更しない・migrationは純追加(expand)」を維持する。**既存カラムの型変更・削除はゼロ**。

```prisma
model Session {
  // ...既存フィールドは変更なし...
  visibility       String    @default("team")  // 既存カラム。取りうる値を "team" | "unlisted" | "public" に拡張（型はStringのまま＝migration不要）
  publicSlug       String?   @unique @db.VarChar(32)  // 追加: 推測不能な公開キー。非公開時はnull
  learningSummary  String?   @db.Text                 // 追加: 学びの要約（昇格時必須）
  publishedAt      DateTime?                          // 追加: 昇格日時（取り消しでnullに戻す）
  publishedById    Int?                               // 追加: 昇格を実行したUser
  publishedBy      User?     @relation("SessionPublisher", fields: [publishedById], references: [id])
  publicViewCount  Int       @default(0)              // 追加: 公開ビューの表示回数（UIには出さない・共有2判定用）
}

model Annotation {
  // ...既存フィールドは変更なし...
  isPublic Boolean @default(false)  // 追加: 既定は非公開。昇格ダイアログで選ばれたものだけtrue
}
```

**設計上の約束**

1. `visibility` は既存の `String` のまま値を増やす。enum化しない理由は、PRD rev.4 の可視性裁定（将来 `followers` が加わる可能性）に対し、enum の値追加migrationを繰り返すより String + アプリ側バリデーションの方が可逆で安いため。値の検証はAPI層で行う
2. `publicSlug` は **crypto.randomBytes(9) の base64url（12文字）**。連番IDを絶対に露出させない（`/p/12` のような推測可能URLは限定公開の意味を失わせる）
3. `publicViewCount` はDBに持つがAPIレスポンスにも画面にも出さない。参照は運用SQLのみ（PRD §6 の計測方法「SQLで見る。ダッシュボードは作らない」と一致）
4. `isPublic` の既定 false は**安全側の初期値**。反省会の生の発言（「なんでここでタックしたの?」等）が昇格操作の副作用で外に出ることは構造的に起こらない

## 5. API 設計

### 5.1 追加エンドポイント

| I/F | 認証 | 入力 | 出力 | エラー |
|---|---|---|---|---|
| `POST /api/sessions/:id/publish` | JWT必須 | `{ visibility: "unlisted"\|"public", learningSummary: string, publicAnnotationIds: number[] }` | `200 { publicSlug, publicUrl, visibility, publishedAt }` | 400（要約空/401字以上・visibility不正・他セッションの注釈ID混入） / 403（uploader本人でもTeam adminでもない） / 404 |
| `POST /api/sessions/:id/unpublish` | JWT必須 | — | `200 { visibility: "team" }` | 403 / 404 |
| `GET /api/public/sessions/:slug` | **不要** | — | `200 { session, tracks, annotations }`（公開用に絞ったペイロード） | 404（存在しない/非公開/取り消し済み） |

### 5.2 公開ペイロードから必ず除外するもの（情報漏洩の防波堤）

`GET /api/public/sessions/:slug` は既存の `GET /api/sessions/:id` を流用せず、**専用のシリアライザを新規に書く**。理由は、既存レスポンスに部内向け情報が含まれるため。除外対象を明示する。

| 項目 | 扱い |
|---|---|
| `rawGpx`（原本GPX） | **除外**（部内版でも除外済みだが、公開ではダウンロードAPI `/api/tracks/:id/gpx` も401/404にする） |
| `isPublic = false` の注釈 | **除外**（レコードごと返さない。件数も出さない） |
| 注釈author・uploaderのemail | **除外**。表示名のみ |
| `teamId` / チームメンバー一覧 | **除外**。チーム表示名のみ |
| `notes`（部内メモ）・`marks`の生座標 | notesは除外。`legs`（レグ境界）は再生に必要なため含める |
| `publicViewCount` | 除外 |

### 5.3 「1方向昇格」と取り消しの関係（裁定が必要な点）

PRD rev.4 の可視性裁定は「チーム→外は**1方向**の公開昇格」である。一方、実務では誤爆の取り消し手段が要る。本書では次のように整理し、承認を求める。

> **提案**: 「1方向」は *日常操作として可視性を上下させるUIを作らない* という意味であって、*取り消し不能* を意味しない。よって取り消し（F-7）は用意する。ただし**取り消すと `publicSlug` を破棄**し、再公開時は**新しいスラッグを発行**する。これにより「一度外に出したURLが、後から中身だけ差し替わって生き続ける」状態を作らない。

### 5.4 レート制限・耐性

公開エンドポイントは認証がないため、既存の部内APIとは別に最低限の防御を置く。

- `GET /api/public/sessions/:slug` に IPあたり 60 req/min の簡易レート制限（新規npm依存を足さず、Expressのメモリ内カウンタで実装。Renderの単一インスタンス前提で十分）
- 存在しないスラッグは**一律404**（「非公開です」と「存在しません」を区別しない＝スラッグ総当たりの手がかりを与えない）
- `publicViewCount` の加算は同一IP・同一スラッグで5分に1回まで（水増し防止）

## 7. リスクと、それに対する設計上の答え

| リスク | 深刻度 | 設計上の答え |
|---|---|---|
| **スコープ膨張でMVPが遅れる**（v1が寄せ集めになった経路と同型） | **高** | 本タスクは S1/S2 の全完了後（T-17・T-20〜T-25の後）にのみ着手する。前倒ししない。§3.2 の「作らないもの」を実装ルールに転記し、逸脱は「発見事項」へ記録して続行 |
| 反省会の生の発言が外に漏れる | **高** | 注釈は既定非公開（`isPublic=false`）＋公開ペイロードのホワイトリスト方式（§5.2）＋除外項目の自動テスト（レスポンスに禁止キーが含まれないことを検証する supertest を必須） |
| 部員の位置情報（自宅周辺等）の露出 | 中 | 航跡は海上のみだが、収録開始/終了が陸上の場合がある。**昇格ダイアログに「航跡の先頭・末尾に陸上の移動が含まれていないか確認してください」の注意書き**を出す（トリミング機能はバックログ。まず注意喚起で運用） |
| ゲートを1段飛ばしたことで、需要のない機能を作る | 中 | 影響は限定的（実装は小さい・§8参照）。かつ本機能自体が計測装置になる（公開URLの実送付回数と`publicViewCount`が共有2の着手条件の実データになる） |
| 未認証エンドポイントの追加による攻撃面の拡大 | 中 | レート制限＋一律404＋ペイロード最小化（§5.4）。Renderの無料枠が公開トラフィックで枯れる懸念は、閲覧が実質数十件想定のため現時点では無視できる |
| スラッグ漏洩（LINE転送等で意図せず拡散） | 低 | `unlisted` の性質上、URLを知る全員が読める。これは仕様であり、昇格ダイアログに「リンクを知っている人は誰でも見られます」と明記する |

## 9. 成功の定義（PRD §6 に追記する内容）

共有1を前倒ししたことで、共有2（Phase 3）への着手条件を実データで判定できるようになる。PRD §6 の該当行を次のように置き換える。

- **（変更前）** 共有0→共有1: Phase 1成功指標①〜③達成＋手動公開投稿で部外反応1件以上
- **（変更後）** 共有1はPhase 1に内包（B案・2026-07-25裁定）。**共有1→共有2の条件**を実測ベースへ変更: ①昇格セッション月2本以上×2ヶ月 ②学びの要約の記入率100%（構造上必須なので自動的に満たす＝実質の条件は①③） ③**部外からの閲覧が発生**（`publicViewCount > 0` のセッションが3本以上、かつ他大学関係者への実送付が2件以上）

非KPI原則は維持する: `publicViewCount` は着手条件の判定にのみ使い、成功指標にもUI表示にもしない。

## 10. 新しく登場する概念・技術（初出の用語説明）

| 用語 | 説明 |
|---|---|
| **unlisted（限定公開）** | 「URLを知っている人だけが見られる」公開状態。YouTubeの限定公開と同じ考え方。アクセス制御ではなく**URLの秘匿性**に依存するため、URLが転送されれば誰でも見られる。だから推測不能なスラッグが必須になる |
| **スラッグ（slug）** | URLの末尾に置く識別子。`/p/8Jq2xNbF4tKa` の後半部分。連番IDだと総当たりで他人のデータを引けてしまうため、暗号論的乱数から作る |
| **base64url** | 乱数バイト列を、URLに安全な64種類の文字（A-Z a-z 0-9 - _）で表現する方式。通常のbase64と違い `+ /` を使わないのでURLエスケープが不要 |
| **OGP（Open Graph Protocol）** | HTMLの`<meta>`タグでページのタイトル・説明・画像を宣言する規格。X・LINE・Slackなどがこれを読んでリンクをカード表示する。**応用**: 就活のポートフォリオでも、GitHub READMEやZennの記事URLがきれいに展開されるかは第一印象に効く |
| **noindex** | 検索エンジンにインデックスしないよう指示するメタタグ。`unlisted` の「検索には出ない」を成立させる（強制力はないが主要検索エンジンは従う） |
| **ホワイトリスト方式のシリアライザ** | APIレスポンスを作るとき「除外するものを列挙する（ブラックリスト）」のではなく「**含めるものだけを列挙する**」実装。将来カラムが増えたときに、うっかり公開されるのを構造的に防ぐ。**応用**: 一般に個人情報を扱うAPI設計の定石 |
