## 1. 目的

**「他部の公開知見が増えたことに、巡回せずに気づける」ようにする。** 共有2まででコンテンツの置き場（チームページ・公開投稿・公開セッション）は揃うが、読者は「あのチームのページをまた見に行く」という能動的な巡回でしか更新を知れない。学連という小さな母集団では巡回の習慣は根付かず、公開した側も反応がなく供給が止まる。フォローと時系列フィードは、この「公開 → 読まれる → また公開する」の循環の**受信側**を最小コストで成立させる装置である。

同時に、**この層は PRD §7 第5リスクが名指しする「作っても過疎で終わる」確率が全段階で最も高い**。学連の母集団は小さく、フォロー先が2人しかいないフィードは機能として成立しない。したがって本書は「どう作るか」と同じ重みで「**どうなったら作らないか**」（§10・§11）を設計対象とする。

非目的（PRD §5-7 非KPI原則の継承）: エンゲージメントの最大化・滞在時間・フォロワー数の競争。フォロワー数は着手条件の判定にのみ使い、成功指標にも画面表示にもしない（§7 で構造として固定する）。

## 2. 完成イメージ

ログイン済みユーザーの体験（すべて既存のデザイントークン `design-system/theme.json` を使用。UI-DESIGN への反映は Team Lead 承認後）:

1. **フォローする** — 公開チームページ `/teams/[slug]` と公開プロフィール `/sailors/[username]` に、ログイン時のみ「フォロー」ボタンが出る。押すと以後そのチーム／個人の公開コンテンツがフィードに流れる。もう一度押せば解除
2. **フィードを見る** — 新規画面 `/feed`（要ログイン）。フォロー中のチーム・個人が公開した**セッション（昇格済み public）と投稿（Entry public / followers）**が、公開日時の新しい順に1本の時系列で並ぶ。並び替え・おすすめ・ランキングは無い。時系列のみ
3. **followers 限定で書く** — 個人文脈の投稿（Entry）の可視性に `followers`（自分のフォロワーだけが読める）が選べるようになる。共有2まで「UIに出さない」とされてきた値の実効化
4. **フォロー先を見つける** — 公開ページを有効化したチームの索引 `/teams`（名前と大学のみの静的な一覧。検索・並び替えなし）から辿れる
5. **見ないもの** — フォロワー数はどの画面にも表示されない。誰かをフォローしても相手に通知は飛ばない。いいね・コメント・リポストのボタンは存在しない

## 4. フォロー主体の設計（誰が誰をフォローするか）

### 4.1 裁定: フォローする側は常に User。される側は「公開 User」と「公開 Team」の2種

| 関係 | 可否 | 根拠 |
|---|---|---|
| User → User（`isProfilePublic=true` のみ） | **○** | PRD §5-1「アカウントは個人のみ」。フォロー対象は公開プロフィールに限る（非公開ユーザーをフォロー可能にすると、フォロー成否が存在オラクルになる） |
| User → Team（`isPublicPageEnabled=true` のみ） | **○** | 供給の主役はチーム文脈（公開セッションはチーム所有）。User フォローだけではプロダクトの核であるセッション昇格を追えない |
| Team → 誰か | **—（存在しない）** | チームはログインの主体ではない（PRD §5-1）。フォローという行為の主語になれない |
| 未公開の User / 未オプトインの Team へのフォロー | **404** | 公開ページ経由でしかフォローボタンに到達できないUIと整合。API 直叩きにも一律404（存在秘匿の統一契約） |

補足裁定:

- **自分自身のフォローは 400**（フィードに自分の投稿を映す意味がない。ミスの検知を早くする）
- **自チームのフォローは許可**する。部内で見えているものと重複するが、禁止する検証コードの方が高くつく（害が無い操作は許す）
- **フォロー後に対象が非公開化（プロフィール非公開・ページ無効化）した場合、購読行は残置**し、配信対象（public コンテンツ）が消えることで自然に流れが止まる。カスケード削除は作らない（再公開時に関係が復元される方が自然で、実装もゼロ）

### 4.2 データモデル（新設1テーブル・純追加）

対象が User と Team の2種であるため、多態参照をどう表現するかが論点。**FK が効く「XOR 2カラム方式」の単一テーブル**とする。

```prisma
// ===== 共有3: フォロー（本SPEC §4。ADR-016案） =====
// 旧 v1 `Follow`（行データ・意味論）は再利用しない（§5.1）。
// テーブル名は 2026-08-02 オーナー裁定により `Follow` を再使用する（§5.2）。
// 前提: BL-01（旧 Follow の DROP・contract migration）が本テーブル新設より【先】に適用されていること

model Follow {
  id         Int      @id @default(autoincrement())
  createdAt  DateTime @default(now())

  followerId Int                     // フォローする側。常に User
  follower   User  @relation("Follower", fields: [followerId], references: [id])

  // --- 対象は User か Team のどちらか一方（XOR。API 400 ＋ migration に CHECK 制約1行） ---
  targetUserId Int?
  targetUser   User? @relation("FollowTarget", fields: [targetUserId], references: [id])
  targetTeamId Int?
  targetTeam   Team? @relation(fields: [targetTeamId], references: [id])

  @@unique([followerId, targetUserId])   // 二重フォロー防止
  @@unique([followerId, targetTeamId])
  @@index([targetUserId])                // 「著者のフォロワーか」判定（§6 followers 認可）用
  @@index([targetTeamId])
}
```

- **XOR の強制**: API 層で「両方指定・両方null は 400」＋ migration SQL に `CHECK ((("targetUserId" IS NULL) <> ("targetTeamId" IS NULL)))` を1行追加。S規模ではAPI検証で足りるが、CHECK は1行のコストで「壊れたデータが入らない」保証が買えるため入れる
- **却下した代替案①: `targetType`＋`targetId` の多態1テーブル** — FK が張れず、User/Team 削除時の整合が手動になる。却下
- **却下した代替案②: `UserFollow`／`TeamFollow` の2テーブル** — FK は綺麗だが、「フォロー中一覧」「フィードのフォロー集合取得」という主要クエリが常に両方を UNION する形になり、コードが単純に2倍になる。対象種別が3つ以上に増える予定は無い（YAGNI）。却下

## 5. ADR-005 の再裁定（Follow テーブルを再利用するか捨てるか）

### 5.1 裁定: **捨てる。** 旧 `Follow` は再利用せず、BL-01（物理削除）の実施条件を「揃った」と判定する

ADR-005（2026-07-24）は「Post/PostLike/Follow は凍結→実運用安定後・オーナー承認で削除。**Follow は共有3設計確定まで物理削除を保留**」とした。本書がその「共有3設計確定」であり、保留を以下のとおり決着させる。

**再利用しない理由（3点。どれか1つでも単独で足りる）**:

1. **形が合わない。** 旧 `Follow` は `followerId`/`followingId` の User→User 専用（`backend/prisma/schema.prisma` L127-138 実確認）。共有3のフォロー対象は User と Team の2種（§4.1）であり、再利用するなら「Team 対象用の列追加＋unique 制約の張り直し」という**既存テーブルの改変**になる。ARCH §3 の原則「既存モデルは変更しない・純追加のみ」に反する上、改変コストは新設と同等以上
2. **意味論が違う。** v1 の Follow は相互SNSの「つながり」で、フォロワー一覧の相互閲覧・通知を前提にした関係だった。共有3のフォローは**公開コンテンツの購読**（フォロワー数非表示・通知なし・§7）。同じ名前の別概念であり、同じ器に入れると将来の読者（implementer・レビュア）が v1 の意味論を引きずる
3. **中身に価値が無い。** 残存する v1 の Follow 行は、410凍結（2026-07-24 ADR-003）から続く旧SNS時代の関係データ。現ユーザー体制（自部のみ・部外登録0件）に対して復元する価値のある購読関係を表していない

**したがって**: ①新テーブルは `Follow` として新設（§4.2。名前の裁定は次項）②旧 `Follow` は Post/PostLike とともに **BL-01（contract migration・DROP TABLE）で物理削除**する。ADR-005 の実施条件「共有3設計確定（＝本書）＋オーナー承認」は**両方とも充足済み**（承認は GATES.md「BL-01（旧Follow の物理削除）の承認」欄に記録）。実施タイミングは Team Lead の判断（同欄）

### 5.2 テーブル名は `Follow` を再使用する（2026-08-02 オーナー裁定による改名。初版の `Subscription` を破棄）

**オーナー裁定**: 「お金は発生しないので名前はフォローに似たもので。既存SNSを参考に」。`Subscription` は既存SNS・決済の文脈で「有料購読（サブスク）」を強く連想させ、無料の purely な購読関係の名前として誤解を招く。UI 語彙（フォロー）・既存SNSの慣習（Follow/follower）とテーブル名・APIパスを一致させる方が、将来の読者（implementer・レビュア）の認知コストが低い。

**初版（2026-08-01）が `Subscription` という別名を選んだ理由は、既に消えている**:

1. 別名の最大の効用は「BL-01（旧 Follow の DROP）と新設 migration の順序独立」＝**BL-01 のオーナー承認が遅れても共有3実装がブロックされない**ことだった。しかし **BL-01 は承認済み**（GATES.md「BL-01（旧Follow の物理削除）の承認」欄。設計確定＋オーナー承認の両条件充足）であり、「承認待ちで新設が塞がる」リスクはもう存在しない
2. もう1つの効用「v2 Follow が復活したという誤読の防止」は、**「旧 Follow の DROP（contract）が先・新 `Follow` の CREATE（expand）が後」という順序を明文の前提にする**ことで代替する。git 履歴上も「消してから、別物を同名で作った」ことが migration の並びとして残るため、行データ・意味論の連続性を誤読する余地はない（旧行が新テーブルに紛れ込む経路は DROP により物理的に存在しない）

**改名に伴う migration の順序依存（重要・初版から変わる点）**:

> **BL-01（M-B・旧 `Follow`/`Post`/`PostLike` の DROP）が先、新 `Follow` の作成（M-A）が後。** この順序を守らない限り Prisma スキーマ上で名前が衝突する。初版が持っていた「M-A と M-B は互いに独立」という性質は改名の対価として失われる（§12.1 を改訂済み）。この対価を受け入れられるのは BL-01 が承認済みだからであり、もし何らかの理由で BL-01 の実施が撤回される場合は本改名も巻き戻して `Subscription` に戻すこと（改名はこの順序前提とセットでのみ有効）。

3. なお「実体は購読だから `Subscription` が正確」という初版の主張は撤回する。正確さは読者に伝わって初めて価値があり、この製品の読者（部員・学連関係者・実装者）にとっての共通語彙は「フォロー」である。命名の最終判断はオーナーのプロダクト裁定に帰属する

**選ばなかった側の最強の擁護論（`Subscription` 維持案）**: 「順序独立という構造上の利点を、語感の好みで手放すのか。BL-01 の実施が何かの事情で無期限に延びれば、共有3実装が2年物の宿題に鎖で繋がれる」— 構造の指摘として正当。ただし①BL-01 は承認済みで、実施は Team Lead の采配1つ（③Gate 優先で「急がない」だけ）であり、実施コストは DROP 3テーブル＋410レジストリ削除のみ ②共有3自体が着手条件未達で最短でも数ヶ月先、BL-01 がそれより遅れる合理的シナリオがない ③万一遅れる場合の巻き戻し手順を上記に明記した、が反駁。

**旧 `Follow` の行データ・意味論を再利用しない判断（§5.1）は本改名と無関係に維持される**——変わるのは「新設テーブルの名前」だけである。

## 6. followers 可視性の実効化（共有2の単一軸のどこに置くか）

### 6.1 裁定: `followers` は**個人文脈の Entry 専用**の第5値。位置は「private より広く、unlisted/public より狭い」認証必須の中間帯

共有2 が確定した単一軸（`private | team | unlisted | public`・`SPEC-share2-team-pages.md` §4.1）に、値 `followers` を**個人文脈（`teamId=null`）に限って**追加する。マトリクスの更新版:

| visibility | チーム文脈（`teamId` あり） | 個人文脈（`teamId=null`） | 閲覧できる人 |
|---|---|---|---|
| `private` | ○ | ○ | author 本人のみ |
| `team` | ○ | — | その teamId の TeamMember |
| **`followers`** | **—（API 400）** | **○（共有3で解禁）** | **author 本人＋author をフォロー中の認証済みユーザー** |
| `unlisted` | ○ | ○ | URL を知っている全員 |
| `public` | ○ | ○ | 全員 |

軸上の順序は `private < team / followers < unlisted < public` と読む。`team` と `followers` は「閉じた読者集合」という同じ階層の別枝であり（部内か、フォロワーか）、上下関係はない。

### 6.2 チーム文脈に置かない理由（400 で拒否し続ける）

1. **PRD rev.4 裁定2 の保証の維持**: 「followers 可視性経由で反省会の生データが部外に漏れる経路は存在しない」はチーム文脈に followers が無いことで構造的に成立している。チーム文脈に置くと「部内より広く、公開より狭い」中間帯が反省会データに生まれ、admin・author・フォロワー集合の3者で読者範囲の認識がずれる事故面になる
2. チーム文脈の外向きは「昇格（1方向操作）で unlisted/public へ」という共有1以来の統一契約。第3の出口を増やすと昇格ダイアログの2択が3択になり、防波堤（明示操作・再同意）の説明が濁る

### 6.3 実装上の性質（共有2の構造を作り直さない）

- **migration 不要**: `visibility` は String＋API層検証（enum 化しない判断は共有2 §4.1 が「将来 followers 追加時に migration 不要で可逆」とまさにこの日のために敷いた設計）。共有3の実装は「`followers` を 400 にしている検証の許可リストに1値足す＋認可分岐を1本足す」だけ
- **publicSlug は発行しない**: `followers` は認証必須の可視性であり、匿名で読める URL とは両立しない。閲覧経路は部内API `GET /api/entries/:id`（認可: author 本人 or `Follow(targetUserId=authorId, followerId=me)` が存在）とフィードのみ。**公開API（`/api/public/**`）には followers 投稿は一切出ない**（禁止キーテストの対象に追加）
- **遷移**: `private ⇄ followers ⇄ public/unlisted` はすべて個人文脈内の操作として可。`followers → private` に戻す操作も可（既読のフォロワーの記憶は消せないが、これは全ての非公開化と同じ限界で、unlisted 取り消しと同じ扱い）
- **フォロー解除・非公開化との関係**: 読者集合は**閲覧時点のフォロー関係で評価**する（スナップショットを持たない）。フォロー解除した人は以後読めなくなる。単純さ優先
- **Session には適用しない**: Session の可視性は `team | unlisted | public` のまま（§3.2）。セッションは常にチーム文脈であり、6.2 がそのまま適用される

### 6.4 この裁定の弱点（自己反論の先出し）

`followers` 投稿は「誰が読めるか」を author が正確に把握しにくい（フォロワー一覧は本人しか見えない設計＝§7 なので author は自分のフォロワー一覧で確認はできるが、フォロワーは今後増減する）。「特定の相手にだけ見せたい」用途には向かず、それは unlisted（URL手渡し）の仕事。作成UIの説明文で「今後あなたをフォローした人も読めます」と明示する。

## 7. API と認可

### 7.1 横断規約（共有2 §7.1 を全面継承）

- エラー形式 `{ error: string }`、存在秘匿が必要な失敗は一律404、カーソルページング `{ items, nextCursor }`（既定20・最大50）、部内APIは JWT＋`wrap()`（ADR-011）
- **レート制限**: フォロー作成は userId 単位 30回/時（M4-01 の教訓「新しく DB 行を作る書き込み口を素通しにしない」）。`GET /api/feed` は認証必須のため公開系の 60req/min は適用しないが、コスト上限として userId 単位 120回/分を置く
- 新設は `/api/follows` 系（テーブル名と同じく 2026-08-02 改名。旧 `Subscription` 案の `/api/subscriptions` は破棄）。**前提順序**: v1 の凍結ルート `/api/follows`（410）は BL-01（M-B）が 410 レジストリから削除するため、**新 `/api/follows` の実装は BL-01 適用後**に行う（テーブルの「drop が先・新設が後」と同じ順序依存＝§5.2。410 レジストリの残骸と新ルートを同居させない）

### 7.2 部内API（JWT 必須）

| I/F | 入力 | 出力 | エラー |
|---|---|---|---|
| `POST /api/follows` | `{ targetType: "user"\|"team", targetUsername? , targetTeamSlug? }` | `201 { follow }`（既フォローなら `200` 既存を返す・冪等） | 400（XOR違反・自分自身）/ 404（対象が非公開・不存在。**区別しない**）/ 429 |
| `DELETE /api/follows` | `{ targetType, targetUsername?/targetTeamSlug? }` | `204`（未フォローでも204・冪等） | 400 |
| `GET /api/follows/mine?cursor=` | — | 自分のフォロー中一覧 `{ items: [{targetType, 表示名, slug/username, createdAt}], nextCursor }` | — |
| `GET /api/follows/followers?cursor=` | — | **自分の**フォロワー一覧（followers 投稿の読者確認用。§6.4） | — |
| `GET /api/feed?cursor=` | — | §8 のフィード | 401 |
| `PATCH /api/entries/:id/visibility`（既存拡張） | `{ visibility: "private"\|"team"\|"followers" }` — `followers` を許可リストへ追加（個人文脈のみ） | 既存契約に追従 | 400（チーム文脈×followers） |

### 7.3 公開APIへの影響

- **新設なし・既存の変更なし。** フォロー関係・フォロワー数は `/api/public/**` のどのペイロードにも**含めない**（禁止キーリストに `Follow` 由来の全フィールドと「フォロワー数・フォロー中数」を追加）
- 公開チーム索引 `/teams`（F-5）は既存 `GET /api/public/teams/:slug` の姉妹として `GET /api/public/teams?cursor=` を新設。返すのは `isPublicPageEnabled=true` のチームの `{ name, university, slug }` のみ（ホワイトリスト方式。オプトインの意味論上、これは既に公開情報の再掲であり新しい露出はゼロ）

### 7.4 認可マトリクス

○=許可 / 404=存在秘匿

| 操作 | 未認証 | 認証済（非フォロワー） | author のフォロワー | author 本人 |
|---|---|---|---|---|
| `followers` 投稿の閲覧（`GET /api/entries/:id`） | 401 | 404 | ○ | ○ |
| `followers` 投稿の編集・削除・可視性変更 | 401 | 404 | ×（閲覧のみ） | ○ |
| `followers` 投稿の公開APIでの取得 | —（**経路が存在しない**。publicSlug 非発行） | — | — | — |
| 他人のフォロー中／フォロワー一覧 | ×（**API が存在しない**） | × | × | ○（自分の分のみ） |
| 非公開 User / 未オプトイン Team へのフォロー | 401 | 404 | — | — |

チーム admin の権限は `followers` 投稿に**及ばない**（個人文脈なので共有2 §5.3 裁定3「個人文脈はチームの管理範囲外」がそのまま適用される。新しい裁定は不要）。

### 7.5 ブロック・ミュートの裁定: **作らない**

要否そのものを裁定する（Issue #4 の設計対象）。**共有3では不要**と裁定する。理由:

1. **フォローされることによる被害経路が存在しない。** 本設計では DM なし・コメントなし・通知なし・フォロワー一覧非公開・いいね無し。フォローは「相手の公開物を読む」だけの一方向購読であり、フォロワーからフォロー対象への到達手段が無い。ブロックが守るべき攻撃面（絡まれる・晒される・通知が飛ぶ）がそもそも作られていない
2. **followers 投稿から特定の人を外したい**という需要は起こりうるが、母集団は実名の学連関係者数十人であり、発生時はオーナー運用（当事者間・管理者対応）で足りる。発生が実測される前にブロック機構（購読の拒否リスト・認可分岐への合流・テスト面の倍増）を作るのは YAGNI
3. ミュート（見たくない人を自分のフィードから消す）は**フォロー解除と等価**。時系列フィードでは「フォローしているのに見たくない」という状態が原理的に薄い（推薦フィードで他人の RT が流れ込む種類の問題が無い）

**再裁定の条件**: followers 投稿の除外需要、またはフォローを起点とする迷惑行為が**1件でも実際に報告されたら**、その時点でブロック（被ブロック者から見えなくなる非対称設計）を最優先バックログに積む。「実測1件で再裁定」と閾値を明記しておく。

## 8. フィードのクエリ・カーソルページング・重複排除

### 8.1 方式: pull 型（閲覧時クエリ）。fan-out（事前タイムライン構築）はしない

フィードの実装方式は大別して pull 型（開いた瞬間に WHERE で引く）と fan-out 型（投稿時に全フォロワーのタイムラインへ行を配る）がある。**pull 型一択**とする。fan-out は数万フォロワー規模で pull の読み負荷が破綻したときの装置であり、本プロダクトの規模（ユーザー数十・コンテンツ数百）では、テーブル1本と整合性バグ（配り漏れ・削除の回収漏れ）を増やすだけで得るものが無い。

### 8.2 フィードに載るもの・載らないもの

| 種別 | 条件 | 載る理由 / 載らない理由 |
|---|---|---|
| Session | `visibility="public"` かつ `teamId ∈ フォロー中チーム` | プロダクトの核。チームの資産なのでチームフォロー経由のみ（昇格実行者は「収録係」であり作品の著者と一致しないため、User フォローでは引かない） |
| Entry（公開） | `visibility="public"` かつ（`teamId ∈ フォロー中チーム` **or** `authorId ∈ フォロー中ユーザー`） | 投稿は個人の著作物でもあるため両経路 |
| Entry（フォロワー限定） | `visibility="followers"` かつ `authorId ∈ フォロー中ユーザー` | フォローしている＝その著者のフォロワーなので、認可条件が購読条件と一致する |
| `unlisted`（Session/Entry） | **載らない** | 「URL を知っている人だけ」の契約（共有2 §7.3）を一覧掲載は破る。共有2 と同じ裁定 |
| `private` / `team` | **載らない** | フィードは部外読者向けの装置。部内の回覧は既存の部内一覧の仕事 |

### 8.3 クエリ（実装の骨子）

1回のリクエストで3クエリ＋アプリ内マージ:

```
follows  = SELECT targetUserId, targetTeamId FROM "Follow" WHERE followerId = :me   -- 数十行
sessions = Session WHERE visibility='public' AND teamId IN (:teams)
             AND (publishedAt, id) < (:cursorTime, :cursorId)     -- カーソル条件
             ORDER BY publishedAt DESC, id DESC LIMIT :limit
entries  = Entry WHERE ( (visibility='public' AND (teamId IN (:teams) OR authorId IN (:users)))
                      OR (visibility='followers' AND authorId IN (:users)) )
             AND (publishedAt, id) < (:cursorTime, :cursorId)
             ORDER BY publishedAt DESC, id DESC LIMIT :limit
→ アプリ側で publishedAt DESC に2列マージし、先頭 limit 件を返す
```

- 並び順キーは **`publishedAt`（外部公開日時）**。`createdAt` ではない（下書きを1ヶ月温めて公開した投稿が1ヶ月前の位置に埋もれるのは時系列フィードとして誤り）。`followers` 投稿は publicSlug を発行しないが `publishedAt` は「followers にした日時」で記録する（列は共有2 の既存定義を流用。意味を「外向き可視化の日時」へ一般化）
- 追加インデックス: `Entry @@index([visibility, publishedAt, id])`・`Session` にも同型（純追加。既存インデックスは触らない）。フォロー集合が IN で数十件・可視性で絞るこの規模では十分
- 応答アイテムはホワイトリスト整形: `{ type: "session"|"entry", title, 表示名(チーム/著者), publishedAt, リンク先, (entryなら) template・boatType名・windMin/Max, (followersなら) "フォロワー限定" バッジ用フラグ }`。内部IDは entry の followers 投稿（部内APIへのリンクに必要）以外は slug 経由

### 8.4 カーソル: `(publishedAt, type, id)` の複合カーソル

- offset 方式は採らない（途中挿入でズレる・深い offset が攻撃面。共有2 §7.1 と同じ理由）
- `publishedAt` 単独カーソルは**同時刻の複数アイテムで欠落・重複が起きる**ため、全順序を `(publishedAt DESC, type, id DESC)` で定義し、`nextCursor = base64url("{publishedAtのISO文字列}:{type}:{id}")` とする。次ページは行値比較 `(publishedAt, id) < (:t, :i)` で引く（同時刻タイの正確な処理はタプル比較。Prisma で表現しにくければ `$queryRaw` ではなく「`publishedAt < :t OR (publishedAt = :t AND id < :i)`」の同値展開で書く）
- カーソルは**復号可能な位置情報のみ**を含む（ユーザーIDや認可情報を入れない。改竄されても他人のデータには到達できない＝毎回 WHERE で認可を評価するため）
- テスト: 「同一 publishedAt を持つアイテム25件を2ページで取得し、欠落0・重複0」を回帰テストに固定（§12）

### 8.5 重複排除

重複の発生源は「同じ Entry がチームフォローと著者フォローの両方にマッチする」ケースだが、**8.3 のクエリは1つの WHERE の OR で書かれているため、1 Entry は最初から1行しか返らない**。fan-out していないので「複数タイムラインに同じ行が配られる」種類の重複も構造的に存在しない。つまり重複排除は**専用ロジックとしては実装しない**（設計で消えている）。防御として「フィード1ページ内に同一 `(type, id)` が2回現れない」ことをテストで固定するに留める。

## 9. 過疎状態／空フィードのUX

**前提: 空であることが正常状態である期間が長い。** 着手条件（部外登録10件）を満たした直後でも、フィードに流れるのは月数件〜十数件と見込むべきで（PRD §6 の供給条件は月4件）、「毎日開いても新着がある」体験は設計目標にしない。フィードは「たまに開くと、前回から増えた分が確実に全部ある」装置として設計する。

### 9.1 3つの空状態（すべて明示的にデザインする）

| 状態 | 条件 | 表示 |
|---|---|---|
| E-1 フォロー0人 | `Follow` 0行 | 「まだ誰もフォローしていません」＋**公開チーム索引 `/teams` への導線**＋「チームページや公開プロフィールのフォローボタンから購読できます」の説明。**コンテンツの流し込みはしない**（下記9.2） |
| E-2 フォロー中・アイテム0件 | 購読はあるが該当コンテンツ0 | 「フォロー中のチーム・ユーザーの公開コンテンツはまだありません。公開されるとここに時系列で並びます」。壊れているのではなく「まだ無い」ことを言い切る |
| E-3 終端 | `nextCursor: null` | 「これで全部です」。無限スピナー・「もっと読み込む」の空振りを出さない |

### 9.2 空フィードに「全体の新着」を流し込まない（意図的な裁定）

E-1 のフォールバックとして「全公開コンテンツの新着」を表示する案は**採らない**。それはフォロー不要の全体フィード（＝§10 の代替案そのもの）であり、①フォローという関係を作る動機を消す ②「とにかく画面を賑やかす」方向はエンゲージメント最適化の入口で、非KPI原則と広報SNS化ドリフト（PRD-rev4 §4-3）の牽制に反する。空の画面には「なぜ空か・どうすれば流れるか」だけを置く。

### 9.3 過疎でも成立させる設計判断（既に各節へ織り込み済みのものの再掲）

- **期間フィルタを付けない**: フィードは全期間を遡れる。「直近7日」等の窓を切ると過疎期はほぼ常に空になる
- **鮮度の演出をしない**: 「N分前」の相対時刻は数ヶ月前のアイテムで過疎を強調してしまうため、日付表示（`2026-08-01`）を基本にする
- **フォロー0でも他ページは完全に機能する**: フィードは追加の受信面であり、チームページ・公開URL・OGP共有という共有1・2の到達経路を何も置き換えない。フィードが過疎でもプロダクトの他の価値は毀損されない（§10 の撤退容易性の根拠でもある）

## 10. 代替案の検討（フィードを作らずに同じ価値を出せないか）

### 10.1 代替案A: 「新着公開コンテンツの横断一覧」（フォロー・フィードを作らない）

**内容**: `/whats-new` のような1ページに、全チーム・全ユーザーの `public` コンテンツを publishedAt 降順で並べるだけ。フォロー関係・Follow テーブル・followers 可視性を一切作らない。実装量は本設計の1/3以下（8.3 のクエリからフォロー集合の絞り込みを外したもの＋画面1枚）。

**この案が強い理由（正面から認める)**: 母集団が小さいうちは、フォローで絞る意味がそもそも無い——全体の新着が月10件なら「全部見る」方が「選んで購読する」より合理的で、フォロー0人の空フィード問題（§9）も原理的に消える。過疎リスクへの耐性は代替案Aの方が高い。

**それでも却下する理由**:

1. **SPEC-share1 §3.2 の明文の裁定と衝突する。** 共有1は「公開セッションの一覧ページ・検索を作らない（入口はURL1本に限定）」と定めた。この裁定の実体は「**本人が渡した相手にだけ届く**」という公開昇格時の同意の範囲であり、横断新着一覧は、昇格した全コンテンツを「誰でも巡回できる棚」へ自動掲載することで、この同意の範囲を事後的に広げる。一方フォローフィードは「公開ページをオプトインした主体を、読者が明示的に購読する」の交差にのみ配信するため、掲載範囲の拡大が**双方の明示操作**に紐づいたまま保たれる。整合の整理: 共有2のチームページは「チーム自身のオプトイン棚」、共有3のフィードは「読者側の購読」、横断一覧だけが「誰の意思にも紐づかない自動掲載」で系から浮く
2. **PRD Phase 4 のスコープ（followers 可視性の実効化）が実現できない。** followers は購読関係が存在して初めて意味を持つ。代替案Aはフィードの代替にはなるがフォローの代替にならず、採用するなら PRD 改訂（Phase 4 の縮小）が必要＝architect が勝手にやってはならない変更（禁止事項）
3. **関係が資産として残らない。** フォローは「どの部がどの部の知見を追っているか」という関係データを蓄積し、学連コミュニティの実在の証明（就活文脈でも、共有4以降があるなら基盤としても）になる。横断一覧は閲覧のたびに消える体験しか残さない

**ただし**、この却下は無条件ではない。§11 の条件に該当する場合、代替案Aを PRD 改訂提案として持ち出すことを本書自身が推奨する。

### 10.2 代替案B: 「フィード画面を作らず、フォロー＋週次ダイジェスト（メール等）」

購読関係だけ作り、閲覧面は作らない案。**却下**: 通知・メール配信は §3.2 で作らないと決めた面であり（開かせる装置・配信基盤の運用コスト）、フィードより重い装置をフィードの代わりに導入するのは本末転倒。

### 10.3 代替案C: 「何も作らない」（共有2の面のみで回す）

チームページ＋URL共有＋OGP だけで回し続ける案。これは「代替案」ではなく**§11 の条件が成立したときの正式な結論**として扱う（着手条件ゲートが既にこの案を既定値にしている、と読むのが正確）。

## 11. 「作らない」判断が正当化される条件

着手条件（§0 の4項目）は「共有3を作ってよい」の必要条件であって十分条件ではない。**4条件を満たしても、以下のいずれかに該当する場合、共有3は作らない（または縮小する）方がよい**と本書は判断する。着手時に architect が数値で回答すること（§13.3 チェックリストに組込み）。

| # | 条件（着手時に SQL / 実測で判定） | 該当時の判断 |
|---|---|---|
| N-1 | **公開ページをオプトインしたチームが3未満**（自部含む） | フォロー対象が実質1〜2主体しかなく、購読は URL ブックマークと等価。作らない。チームが増えるまで待つ |
| N-2 | **直近8週の public 昇格＋public 投稿の合算が月10件未満** | フィードを開いても前回から1〜2行しか増えない。フォローで絞る意味が無い＝§10.1 の「代替案Aが強い」状況そのもの。フィードを作らず、代替案A（横断新着一覧）を **PRD 改訂提案**（SPEC-share1 §3.2 の裁定変更を含む）として Team Lead / product-lead へ出す方が正しい |

## 13. リスクと自己反論

### 13.1 本設計への最強の反論 — 「これは2段先の在庫設計であり、共有2 SPEC よりさらに腐りやすい。しかも §11 で自分で『たぶん作らない方がよい』と言っている」

正面から認める。共有2の実測（K1 投稿者数・K2 投稿ペース・K4 部外投稿= `SPEC-share2-team-pages.md` §13.2）が1つも出ていない段階で、フォロー主体・フィードの形を固定するのは、設計在庫のリスクとしては共有2 SPEC 執筆時（§13.1 で同じ自己反論をした）より一段悪い。着手時に前提が変わっている確率は高く、**本書の実装詳細（§7・§8・§12）は着手時に3〜5割書き直す前提**で読まれるべきである。

これへの答え: ①本書の中核は実装詳細ではなく**腐らない構造裁定**——ADR-005 の決着（§5。これは実装しなくても今価値がある: 2年塩漬けの保留を閉じ、BL-01 をオーナー承認待ちだけにした）、followers の置き場（§6。共有2実装が「将来値の余地」を推測で作るのを防ぐ）、非KPI原則の構造化（フォロワー数をAPIに出さない）、作らない条件の数値化（§11）——であり、これらは供給の実測に依存しない ②実測依存部分は §13.3 チェックリストが着手時の再検証を強制する ③「たぶん作らない」と書いた設計書は無駄ではない。着手判定を印象ではなく数値（N-1〜N-4）で下せるようにすることが、この層では設計そのものより価値が高い。

## 14. ARCH.md への提案（ADR文面）

> **ARCH.md への実際の追記は Team Lead が行う（本書は文面の提案まで。既存正本は未変更）。** ADR-005 本文には「→ 再裁定は ADR-016（2026-08-01）で決着」の相互参照追記を併せて提案する。

### 14.1 ADR-016 案（ADR-005 の決着）

> ### ADR-016: 旧 Follow は再利用せず物理削除（BL-01・オーナー承認済み）。フォローは旧テーブルの drop 後に新テーブル `Follow`（User→公開User/公開Team・XOR 2カラム）として新設する
> - **状況:** ADR-005 が「Follow の物理削除は共有3設計確定まで保留」としていた。共有3の詳細設計（SPEC-share3-follow-feed.md・Issue #4）で決着させる。初版（2026-08-01）は新テーブル名を `Subscription` としたが、2026-08-02 オーナー裁定（「お金は発生しないので名前はフォローに似たもので。既存SNSを参考に」）により `Follow` へ改名
> - **決定:** ①旧 `Follow` は再利用しない（行データ・意味論とも）。Post/PostLike とともに BL-01（contract migration）で物理削除する。実施条件「共有3設計確定＋オーナー承認」は**両方充足済み**（承認は GATES.md 記録） ②新フォローは `Follow` として新設。フォローする側は常に User、対象は公開 User または公開 Team の XOR 2カラム（FK＋CHECK 制約）③**migration は「BL-01 の DROP（contract）が先・新 `Follow` の CREATE（expand）が後」の順序を必須とする**（同名衝突の回避。対応する API も旧 `/api/follows`(410) のレジストリ削除後に新 `/api/follows` を実装する）
> - **理由:** 旧 Follow は User→User 専用で Team フォローに形が合わず、拡張は「既存モデル無改変」原則（ARCH §3）に反する。v1 の関係データは購読として復元する価値が無く、温存すると初回フィードに覚えのない配信が混ざる。名前は UI 語彙（フォロー）・既存SNS慣習と一致させる（`Subscription` は有料購読の誤連想）。詳細は SPEC-share3 §5
> - **選ばなかった側の最強の擁護論:** （再利用案）「テーブルは既にあり、列を足す方が migration が小さい」— 行数の節約は、3回の漏洩事故を経て確立した無改変原則と交換しない、が反駁。（`Subscription` 維持案）「別名なら BL-01 と新設が順序独立で、BL-01 の遅延が共有3をブロックしない」— 初版がこの理由で別名を選んだのは正しかったが、BL-01 承認済みの現在は守るものが無い保険であり、巻き戻し条件（BL-01 撤回時は `Subscription` へ戻す）を SPEC §5.2 に明記して手放す、が反駁
> - **結果として受け入れるデメリット:** ①BL-01 実施までスキーマに旧 `Follow`（死・削除待ち）が残り、新設はその実施を待つ（順序制約の発生。初版の順序独立性は改名の対価として喪失）②同名テーブルが「消えて・別物として再生した」履歴になるため、将来の考古学には migration の並び順の読解が必要（ADR と SPEC §5.2 が注記で補う）

### 14.2 ADR-017 案（フィードとフォローの設計原則）

> ### ADR-017: フィードは pull 型・時系列のみ・publishedAt 複合カーソル。followers 可視性は個人文脈 Entry 専用。フォロワー数は API に出さない。ブロック・ミュートは作らない
> - **状況:** 共有3（フォロー／フィード）の方式選定（SPEC-share3-follow-feed.md）
> - **決定:** ①フィードは閲覧時クエリ（pull）で構築し、fan-out（事前タイムライン）はしない ②並びは `(publishedAt DESC, type, id DESC)` の複合カーソルページングのみ。推薦・ランキング・既読管理なし ③`followers` は可視性軸の第5値として**個人文脈の Entry に限り**追加（チーム文脈は400のまま＝「followers 経由で反省会データが漏れる経路は無い」の保証維持）。publicSlug は発行しない ④フォロワー数・フォロー関係は `/api/public/**` にも部内APIにも出さない（本人の一覧のみ）⑤ブロック・ミュートは作らない（DM・コメント・通知・フォロワー一覧公開が無く、被フォローの被害経路が存在しないため。迷惑事案の実測1件で再裁定）
> - **理由:** 規模（ユーザー数十・行数百）で fan-out は整合性バグの純増。非KPI 原則（PRD §5-7）は UI の自制でなく API の出口で構造化する。詳細は SPEC-share3 §6〜§8
> - **選ばなかった側の最強の擁護論（横断新着一覧で足りる＝フォロー不要論):** 「母集団が小さい間は全体新着の方が合理的で、空フィード問題も消える」— 過疎耐性の指摘として正当。ただし横断一覧は SPEC-share1 §3.2 の裁定（公開一覧を作らない＝昇格時の同意範囲）と衝突し、followers 可視性の実現手段も持たない。なお供給が SPEC-share3 §11 N-2 の閾値を下回る場合は、フィードを作らずこの案を PRD 改訂として持ち出すことを SPEC 自身が推奨している、が整理
> - **結果として受け入れるデメリット:** フォロー数千規模になった場合 pull は再設計になる（その閾値で fan-out を検討）。followers 投稿の読者範囲は動的（今後のフォロワーも読める）で、誤解の残余リスクは UI 文言で緩和するに留まる
