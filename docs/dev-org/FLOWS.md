## 図1: イベントフロー図（1週間の運用サイクル）

E2（自前収録型リプレイ・デバッガ）主役の場合に、部の1週間でsailvlogがどう使われるかを時系列で示す。

```mermaid
sequenceDiagram
    actor Bu as 部員
    actor Mane as マネ艇担当
    actor Owner as オーナー・主将
    participant Sys as sailvlog

    Note over Bu,Sys: 出艇前（練習当日）
    Bu->>Sys: 過去セッションを閲覧（前回の反省点を確認）
    Mane->>Mane: Geo Tracker収録開始
    Bu->>Bu: 各艇でもGPX収録開始（任意）

    Note over Bu,Mane: 練習中〜着艇後
    Bu->>Mane: 着艇後、収録停止しGPXを共有
    Mane->>Mane: 自艇分も収録停止

    Note over Mane,Sys: アップロード
    Mane->>Sys: 複数艇ぶんのGPXをアップロード（艇名ラベル付け）
    Sys->>Sys: 1Hzグリッド正規化・1セッションにまとめる

    Note over Owner,Sys: 反省会（プロジェクタ）
    Owner->>Sys: セッションを開いて再生
    Owner->>Sys: レグ頭出し・2艇比較で議論を進行
    Owner->>Sys: タイムラインに注釈を書き込み
    Bu->>Sys: 同席メンバーも議論を踏まえて注釈追加

    Note over Bu,Sys: 事後
    Bu->>Sys: 注釈込みURLをスマホで見返す

    Note over Bu,Sys: 蓄積 → 翌週へ
    Bu->>Sys: 次回出艇前に本セッションを再度参照（1周目に戻る）
```

**読み方**
- 「読む」（出艇前・反省会）と「書く」（着艇後・反省会）が分離しているのは、PRD §3の利用文脈をそのまま反映している。マネ艇担当は操作ほぼゼロが要件なので、練習中の関与は収録開始/停止のみ。
- アップロードを行うのはマネ艇担当1人（=供給の担い手が録る係に集約される、というPRD §4のE2推奨根拠）。部員各自のGPXはマネ艇担当に集約されてからまとめてアップロードされる想定で、部員が個別にsailvlogへアクセスするのは着艇後の送付までではない。
- 反省会はオーナー・主将が再生操作を進行し、注釈は同席する部員も書き込める前提（PRDの「反省会での注釈」を1人に限定していない）。
- 最終行（次週出艇前の参照）が「蓄積」を表す。データが練習を重ねるごとに資産として積み上がる構造がこの1周のループで閉じている。

## 図2: 画面遷移図（MVPの画面のみ）

TASKS.md S1/S2で実装される画面のみを対象にする。凍結画面（Article/Question/Learn/フィード等）はこの図に含めない。

```mermaid
flowchart TD
    Login["ログイン画面（v1流用）
    部員・マネ艇担当・オーナーが認証する入口"]
    List["セッション一覧（部内）
    Team内の練習/レースをメタ情報一覧で表示"]
    Upload["セッションアップロード
    GPX複数選択→艇名ラベル付け→保存"]
    Replay["リプレイ画面
    再生/一時停止/シーク・レグ頭出し・2艇比較・注釈タイムライン"]
    Share["注釈込み共有URL
    リプレイ画面の特定状態（時刻・艇選択・レグ）への直リンク"]
    Publish["公開昇格ダイアログ（共有1）
    学びの要約・公開するメモの選別・公開範囲"]
    Public["公開ビュー /p/slug（共有1）
    部外がログインなしで読む・読み取り専用"]

    Login --> List
    List --> Upload
    Upload -->|保存後、そのセッションを開く| Replay
    Upload -->|一覧に戻る| List
    List -->|既存セッションを開く| Replay
    Replay -->|現在の再生状態のURLをコピー| Share
    Share -->|URLを開くと再生状態を復元| Replay
    Replay -->|uploader/管理者のみ「公開する」| Publish
    Publish -->|公開URLを発行| Public
    Publish -->|公開をやめる（URLは失効・再公開は別URL）| Replay
```

**読み方**
- 一覧・アップロード・リプレイの3画面がMVPの本体で、共有URLはリプレイ画面の「別の入口」（新規画面ではなく状態の直リンク）にすぎない。
- 「保存後リプレイへ」の分岐は、マネ艇担当がアップロード直後に取り込み結果を確認する動線を想定している。一覧に戻る分岐も残しているのは、複数セッションをまとめて登録する運用を妨げないため。
- ログイン以降どの画面からも一覧に戻れる想定だが、図では主要遷移のみ描いている（ブラウザバック等の副経路は省略）。

- **公開昇格（共有1）は2026-07-25にPhase 1へ前倒しされた**（PRD rev.6・`SPEC-share1-phase1.md`）。図では破線的な位置づけ＝**S1/S2の全実装が終わってから着手する末尾機能**であり、週次サイクル（図1）の必須動線ではない。図1のループは公開なしで完結する（部内の振り返りが本体で、公開は「外に見せたいものが出たときだけ」の追加動作）
- 公開ビュー`/p/slug`は**部外の人がログインなしで読む唯一の入口**。ここから一覧・検索・登録・フォローへは進めない（意図的にURL1本に限定。`SPEC-share1-phase1.md` §3.2）

**注記（図外）**: Article/Question/Learn/フィード等の既存画面は凍結済み・遷移なし（ARCH.md ADR-003）。上記2図には含めていない。
