## 0. この文書が決めること

PRD §5 Phase 3（共有2）＝「チームページ＋個人プロフィール＋投稿」の詳細仕様（データモデル・ライフサイクル・所有文脈と可視性のマトリクス・API・認可・画面・migration・テスト・実装スライス）を、implementer が着手条件達成後に迷わず実装できる粒度で確定する。

**前提となるオーナー裁定（2026-08-01・3点）**:

1. **投稿をプライベートにできる**（PRD rev.4 の「所有文脈 × public/followers/private」裁定と整合）
2. **投稿時に「所属」を選べる**（個人として投稿する／チームとして投稿する。Qiita の Organization 投稿に相当）
3. **投稿の本文は Markdown の自由記述を基本とし、「セッティングカード」「練習／レース振り返り」は下書きの出発点となる選べるテンプレートとして提供する**（フィールドの強制ではない。Qiita の実際の姿と同じ構造）

裁定3は **PRD §5 の「テンプレ限定・自由記述は解禁しない」と真正面から矛盾する**ため、§10 に PRD 改訂提案を同梱した（改訂の実施は Team Lead / product-lead）。また、PRD がその禁止を置いた理由（「供給源なき投稿箱は v1 が死んだ構造の再演」）への設計上の回答を §3.3・§13 に示す。

**追加の前提となるオーナー裁定（2026-08-02・6点。根拠は GATES.md 末尾）**:

4. **タグを投稿に付ける**（語彙はヨットの実務語＋`開発ログ`。**当面クリック不可**＝§3.4）
5. **「道具・装備レビュー」テンプレを追加**（テンプレは3種になる。商品マスタ・星評価・購入導線は作らない＝§3.2）
6. **ストック（あとで読む）を追加**（完全非公開。author 本人にも見えない＝§4.4・§7.5）
7. **ヘッダーメニュー（ログイン済み）を「つくる／じぶんの／全体」の3束で設計する**（§8.1）
8. **記事ごとの公開範囲のUI表現を確定**（公開・限定公開・非公開の3択と §2.2 の4値の対応＝§2.5）
9. **チーム公開ページのメンバー欄は同意者0人でもタブを出す**（空は「メンバーなし」表示。§15 旧論点4の決着）

**本改訂は設計のみであり、実装着手条件（PRD §6・冒頭表）が未達である事実は一切変わらない。**

## 1. 目的 — なぜこの層を作るか

| 目的 | 内容 |
|---|---|
| ① 部のショーケース | 公開昇格されたセッション・投稿・チーム紹介が1つのURL（`/teams/[slug]`）に並ぶ。新歓ビラ・部のXに貼れる「フォロワーゼロでも意味がある」ページ（PRD-rev4 §2: 団体ページをフォローより先に置く根拠） |
| ② 実践知の蓄積 | 反省会の副産物（振り返り・セッティング）と、型に収まらない知見（レース戦術・艤装・体づくり・代替わりの引き継ぎ）を、同じ器に書き残せる。テンプレートが「何を書けばいいか」を supply し、自由記述が「型に収まらないもの」を受け止める |
| ③ リプレイとの複利 | 投稿はリプレイ（Session）にリンクできる。「この航跡のときのリグ設定」「この練習の振り返り」が繋がり、単体ブログでもリプレイ単体でもない価値になる |
| ④ 共有3の判定装置 | 共有2→共有3 の着手条件（PRD §6）と、本書 §13 の「失敗の早期検知」計測の土台になる |

**この4つに共通するのは「知を器に並べて外へ開く」ことであり、SNS を作ることではない。** フォロー・フィード・いいねは本スコープに一切含まない（§3.2）。

## 2. 完成イメージ — ユーザーが何を見て何ができるようになるか

### 2.1 投稿の作成（部内・ログイン必須）

新規作成はテンプレート選択から始まる。**白紙から始めさせない**（空のエディタは v1 の失敗構造。テンプレが「何を書く場か」の輪郭を作る）:

```
新しい投稿
┌──────────────┬──────────────┬──────────────┬─────────────┐
│ 📋 セッティングカード │ 🔁 練習/レースの振り返り │ 🔧 道具・装備レビュー   │ ✏️ 白紙から書く    │
│ 艇種×風速×設定値を   │ 状況→試した→わかった→  │ 何を・いくらで・もったか │ 型に収まらない知見  │
│ 記録する            │ 次に試す の議事構造     │ ・次も買うか           │ （戦術・引き継ぎ）  │
└──────────────┴──────────────┴──────────────┴─────────────┘
所属: [○○大学ヨット部として ▼ / 個人として]
```

（テンプレ3種目「道具・装備レビュー」は 2026-08-02 オーナー裁定。雛形の見出し構成は §2.6）

テンプレートを選ぶと、**Markdown 下書きに雛形が差し込まれる**（フィールド強制ではない。消しても崩しても良い）:

```
タイトル [7/20 定期練習ふりかえり]
所属 [○○大学ヨット部 ▼]   リンクするリプレイ [江の島 7/20 ▼]（任意）
タグ [セッティング ×] [スタート ×] [＋タグを追加 ▼]（固定語彙から最大5つ・任意。§3.4）
┌─ 本文（Markdown）──────────────────────────┐
│ ## 状況・条件                                    │
│ （風速・風向・波・海面。例: 南西 8-12kt、波高0.5m）   │
│ ## 試したこと                                    │
│ ## わかったこと                                  │
│ ## 次に試すこと                                  │
└──────────────────────────────────────┘
（セッティングカード選択時のみ）艇種 [470▼] 風速 [8]〜[12]kt ← 図鑑フィルタ用・任意
[保存（自分のみ）] [部内に公開]
```

- リプレイ画面の「振り返りを書く」導線からは、該当テンプレ＋セッション情報（日付・場所・リンク）が**差し込み済み**の状態で開く（書き始めの摩擦を最小化）
- 本文はMarkdown。プレビュー付き。画像は外部URLの埋め込みのみ（アップロードは作らない＝§3.2）

### 2.2 投稿のライフサイクル（Qiita との対応）

| sailvlog | Qiita相当 | 意味 |
|---|---|---|
| `private` | 非公開（下書き） | **本人のみ**。下書きもこれ（「下書き」という別状態は持たない＝同じ概念を2つの名前で持たない） |
| `team` | Organization 内限定 | 部内メンバーのみ。チーム文脈投稿の既定の公開先 |
| `unlisted` | **限定共有記事** | URLを知っている人だけ。共有1の `unlisted` と**同一概念・同一実装**（推測不能スラッグ） |
| `public` | 公開記事 | 誰でも読める。チームページ／プロフィールにも並ぶ |

### 2.3 チーム公開ページ `/teams/[slug]`（認証不要・**オプトインしたチームのみ**）

```
┌─────────────────────────────────────────────────┐
│ sailvlog                              [これは何?] │
├─────────────────────────────────────────────────┤
│ ⛵ ○○大学ヨット部        長崎 / 470・Snipe        │
│ 「週次反省会をリプレイで回しています。…」(公開bio)  │
├─────────────────────────────────────────────────┤
│ [公開リプレイ] [投稿] [メンバー]                    │
├─────────────────────────────────────────────────┤
│ ▸ 微風域の470基本セット      📋カード 470 8-12kt   │
│ ▸ 7/20 定期練習ふりかえり    🔁振り返り            │
│ ▸ 新入生に伝えたい艤装チェックリスト                │
│              （public のみ。カード絞り込みチップ有） │
└─────────────────────────────────────────────────┘
```

- タブは3つ: 公開リプレイ（共有1の昇格セッション）／投稿（public のみ）／メンバー（**掲載に本人が同意した部員のみ**）
- **メンバータブは同意者が0人でも出す。空のときは「メンバーなし」と表示する**（2026-08-02 オーナー裁定＝旧 §15 論点4の決着。タブごと消す案は不採用。空表示は「非公開にしている」とも「部員がいない」とも断定しない中立の文言とし、同意者の存在有無を外部から推定させない点でも都合がよい）
- **公開ページはチーム admin が明示的に有効化した場合のみ存在する**（既定は無効＝従来どおり非メンバーには404）

### 2.4 公開投稿 `/posts/[slug]` と個人プロフィール `/sailors/[username]`

- 公開投稿: 認証不要・読み取り専用・OGP付き。部外の閲覧者は**読むだけ**（コメント・いいね・登録導線なし＝共有1と同じ）
- 個人プロフィール: 表示名・艇種・自己紹介＋自分の public 投稿・関与した公開セッション。**本人がオプトインした場合のみ**存在（既定オフ）。v1 の `GET /api/sailors/:username` 410凍結は継続し、公開専用ホワイトリストAPIを新設する（ADR-009 の擁護論で予告済みの方式）

### 2.5 公開範囲のUI表現（2026-08-02 裁定。§2.2 の4値は変えず、見せ方だけを確定する）

エディタの公開範囲は**新しい可視性値の追加ではない**。§2.2 で確定済みの単一軸 `private/team/unlisted/public` を、書き手に見せる語へ写像する:

| エディタ上のラベル | 対応する値 | 補足説明（UI に添える一文） |
|---|---|---|
| **非公開** | `private` | 「自分だけが見られます。書きかけの置き場としても使えます」 |
| **部内に公開**（チーム文脈のみ表示） | `team` | 「○○大学ヨット部のメンバーだけが見られます」 |
| **限定公開** | `unlisted` | 「リンクを知っている人は誰でも見られます」（共有1の昇格ダイアログと同一文言） |
| **公開** | `public` | 「誰でも見られます。チームページ／プロフィールにも並びます」 |

- **個人文脈（`teamId=null`）ではオーナー裁定どおりの3択**（非公開・限定公開・公開）。`team` は §5.1 のとおり個人文脈に存在しないため、選択肢ごと表示しない
- **チーム文脈では「部内に公開」を加えた4択**になる。3択に無理に収めるために `team` を「非公開」へ合流させる案は採らない——「自分だけ」と「部内全員」は読者集合がまったく違い、同じラベルに畳むと誤爆（下書きのつもりが部内に見えていた）の温床になる
- 外向き2値（限定公開・公開）への遷移は従来どおり**昇格ダイアログ経由の明示操作**（§5.2）。エディタのプルダウンで直接 `public` に落とせるようにはしない（チーム文脈の1方向制約と再同意の防波堤を維持）
- **設計意図の明記: 「非公開」は書きかけを置いておける場所である。** まだ分かっていないことを途中まで書ける——これが供給を生む鍵であり、完成した知見しか置けない場所には誰も書かない。UI 文言・ヘルプでも「下書き置き場」としての用途を積極的に案内する（§2.2 の「下書きという別状態は持たない」判断と対）

### 2.6 「道具・装備レビュー」テンプレの雛形（2026-08-02 裁定でテンプレは3種に）

```
## 何を使ったか
（品名・型番・メーカー。例: ◯◯社 △△グローブ 3シーズンモデル）
## いくらで・どこで買ったか
## どれくらいもったか
（使用頻度と期間。例: 週2練習で1シーズン）
## 次も買うか
（買う／買わない と、その理由）
## 注意点
（サイズ感・手入れ・こういう人には向かない 等）
```

- 他テンプレと同じく**下書きへの差し込みのみ**（フィールド強制ではない。消しても崩してもよい）。`template` 列の値は `"gear-review"`
- タグ `道具`・`艤装` が既定で付与された状態で開く（外せる。§3.4）
- **このテンプレは「器の追加」であって「レビュー機能の追加」ではない。** 商品マスタ・星評価・購入導線は作らない（§3.2 に追記。理由は GATES.md 2026-08-02 裁定に記録: 供給が育つ前の商品マスタは空の棚と表記ゆれだけが残る／星評価の集計は PRD §5 のランキング禁止と衝突し、部員10人規模では低評価者が事実上特定され道具の話が人の話になる／購入導線は税務・規約・責任の問題を持ち込む）。再検討トリガはオーナー裁定どおり「レビュー投稿が実際に溜まり、横断で見たい要求が実測で出たとき」

## 3. 実装する機能の一覧

### 3.1 作るもの

| # | 機能 | 内容 |
|---|---|---|
| G-1 | 投稿（Entry） | Markdown 自由記述＋タイトル＋任意メタ（艇種・風速帯）＋Session リンク任意。単一モデル（§4） |
| G-2 | テンプレート**3種** | 「セッティングカード」「練習／レース振り返り」「**道具・装備レビュー**」（3種目は2026-08-02裁定・§2.6）。新規作成時に下書きへ差し込む雛形（フロントの定数。DBに雛形は持たない）。どのテンプレ経由かを `template` 列に記録（供給計測用＝§13） |
| G-3 | 所属の選択 | 投稿時に「チームとして／個人として」を選ぶ（`teamId` の有無）。**作成後の付け替えは不可**（§5.3 裁定1） |
| G-4 | 4値可視性 | `private / team / unlisted / public`（§2.2）。部内側の遷移（private⇄team）は日常操作、外向き昇格（→unlisted/public）は共有1と同型の1方向操作＋取り消しでスラッグ破棄 |
| G-5 | チーム公開ページ | `/teams/[slug]`。**admin のオプトイン制**（既定無効）。公開bio・公開セッション・public投稿・同意済みメンバー |
| G-6 | メンバー掲載の個人同意 | 公開ページの「メンバー」欄は本人同意（既定オフ）のみ掲載 |
| G-7 | 個人プロフィール公開 | `/sailors/[username]`。本人オプトイン制（既定オフ）。公開専用ホワイトリストAPI新設 |
| G-8 | 部内投稿一覧＋図鑑フィルタ | `/posts`（部内）。艇種×風速メタでの絞り込み（メタ付き投稿＝主にカードが対象） |
| G-9 | Markdownレンダリング | raw HTML 無効・React要素として描画（XSS防波堤。§7）。**新規npm依存1件が必要＝Team Lead 承認制**（ARCH §1・実装ルール6） |
| G-10 | OGP | 公開投稿・チームページに `generateMetadata`。共有1と同じ静的画像＋動的テキスト。unlisted は `noindex` |
| G-11 | タグ（表示のみ・辿れない） | 固定語彙・最大5つ・任意。投稿カード／詳細に表示するが、**タグ一覧ページ・タグ検索・クリック遷移は作らない**（§3.4。2026-08-02裁定） |
| G-12 | ストック（あとで読む） | User×Entry の完全非公開ブックマーク。**誰にも（記事の author にも）見えず、数もどこにも出さない**（§4.4・§7.5・§8。2026-08-02裁定） |
| G-13 | ヘッダーメニューの情報設計 | ログイン済みナビを「つくる／じぶんの／全体」の3束に整理（§8.1。2026-08-02裁定） |

### 3.2 明示的に作らないもの（スコープ膨張の防波堤。共有1 §3.2 を継承・拡張）

- **フォロー・フィード・followers 可視性** — 共有3（Phase 4）。Follow テーブルの裁定は共有3設計（SPEC-share3 §5）で決着済み: 旧 Follow は物理削除（**BL-01 オーナー承認済み＝GATES.md**）、新設は共有3の `Follow`（2026-08-02 改名裁定。SPEC-share3 §5.2）。共有2は購読関係を一切作らない
- **いいね・ランキング・推薦アルゴリズム・DM／チャット・ゲーミフィケーション** — PRD §5 恒久禁止。**ストック（G-12）がいいねの裏口にならないよう、ストックは完全非公開・数もどこにも出さない**（§4.4）
- **サイト横断の公開投稿一覧・検索・タグ検索** — 公開側の入口は「チームページ」「個人プロフィール」「投稿URL」の3つだけ。供給が育つ前に「空の棚」を見せない（v1 の失敗構造）。**タグは付与・表示のみ**（固定語彙・§3.4）とし、タグ一覧ページ・タグ検索・クリック遷移は本禁止に含まれるため作らない。図鑑軸（艇種・風速）は従来どおり第一級メタで扱う
- **商品マスタ**（型番・メーカー・価格の構造化DB）— 供給が育つ前に作ると、空のマスタと表記ゆれだけが残る（2026-08-02裁定・GATES.md）
- **星評価・評価の集計** — PRD §5 のランキング禁止と衝突する。加えて部員10人規模では「誰が低評価を付けたか」が事実上特定でき、道具の話が人の話になる（同裁定）
- **購入導線（EC連携・アフィリエイト）** — 税務・規約・責任の問題を持ち込む。MVPの外（同裁定）
- **公開側コメント・アカウント登録導線の強制** — 共有1と同じ。公開ビューは完全匿名で読める
- **画像・ファイルアップロード** — ストレージ基盤（S3等・新規インフラ＋コスト）が必要。本文への画像は外部URL埋め込みのみで開始し、供給が実証されたらバックログから昇格
- **編集履歴・版管理** — `updatedAt` のみ（§5.3 裁定4）。履歴テーブルは需要が出てから
- **通報・モデレーション管理画面** — 読者数十人規模に管理画面は過剰。モデレーションは権限設計＋運用で行う（§5.3 裁定3・§8）
- **チーム slug の変更（rename）・チーム検索・閲覧数のUI表示** — YAGNI／非KPI原則（PRD §5-7）

### 3.3 「供給源なき投稿箱」への設計上の回答（PRD §5 が禁止を置いた理由に正面から答える）

v1 が死んだ構造は「**書く動機の供給源がないまま自由投稿の器だけがある**」ことだった。自由記述を本線にする本裁定は、その防波堤を1つ外す。代わりに何がその役目を負うか:

1. **書き始めの供給源は「反省会の副産物」に固定する。** 主動線はリプレイ画面からの「振り返りを書く」（テンプレ＋セッション情報差し込み済み）。ゼロから書く動機に賭けず、**既に起きた練習・反省会に寄生**する（E2 が反省会に寄生したのと同じ原理）
2. **白紙を最初に見せない。** 新規作成は必ずテンプレ選択から（§2.1）。白紙は3番目の選択肢であり既定にしない。「何を書けばいいか分からない」への答えは、雛形の見出し（状況→試した→わかった→次）が book of prompts として機能すること
3. **Qiita との非対称性を認める。** Qiita が成立するのは母数（数十万人）が大きく、個人の問題解決記録が自然発生するからである。**部員10人規模で同じ力学が働く保証はどこにもない**。「Qiita と同じ形にすれば動く」とは本書は主張しない。主張するのは「形は Qiita 型が最も摩擦が低く、供給は反省会への寄生で作り、**機能したかは計測で判定する**」ことだけ
4. **失敗を早期に検知する計測を定義する**（§13.2。数値・観測方法・未達時のアクションまで）。防波堤を「禁止」から「計測ゲート」へ置き換えるのが本裁定の実体である

### 3.4 タグ — 「表示はするが辿れない」段階として設計する（2026-08-02 裁定）

**タグは当面クリック不可である。** タグ一覧ページ・タグ検索・タグをキーにした横断一覧は作らない。理由: それらは §3.2 が禁じる「サイト横断の公開投稿一覧・検索・タグ機能」そのものであり、供給が育つ前に空の棚（投稿0件のタグページ）を見せることは v1 の失敗構造の再演になるため。**現段階のタグの仕事は分類の入口ではなく「何の話かをひと目で伝えるラベル」だけ**である。

| 論点 | 裁定（architect・2026-08-02。Architecture Gate で確認対象） | 根拠 |
|---|---|---|
| 語彙 | **固定語彙のみ。自由入力は許さない**: `クローズホールド` `リーチング` `サークリング` `セッティング` `スタート` `艤装` `道具` `開発ログ` の8語（オーナー指定の実務語7＋制作記録用1） | ①自由入力は表記ゆれ（「艤装/ギソウ/rigging」）を必ず生み、クリック可能化の解禁時に統合作業が発生する。固定なら解禁が語彙の再編なしで済む ②固定語彙は「この場は何を書く場か」の輪郭（book of prompts）としても機能し、テンプレと同じ供給装置になる ③商品マスタを作らない裁定と同型——構造は供給が実証されてから育てる |
| 上限 | **1投稿5つまで**（0でもよい・任意） | クリック不可の現段階でタグは純粋にラベルであり、8語中5つを超えて付く投稿は分類として機能していない。UI 上も5チップで折り返しなく収まる |
| 語彙の追加 | **オーナー裁定制**（フロント＋API共有の定数1箇所を変更）。部員からの追加要望は Team Lead 経由でオーナーへ | 語彙は製品の輪郭でありプロダクト判断。実際に 2026-08-02 に `艤装` `道具` がオーナー裁定で追加された前例に従う |
| 保存形式 | `Entry.tags String[]`（PostgreSQL 配列・既定 `[]`）。**v1 の `Tag`/`ArticleTag` は再利用しない**（410凍結継続・§6） | 固定語彙8語・検索しない現段階で正規化テーブル（Tag＋中間テーブル）は過剰。クリック可能化の解禁時も `WHERE :tag = ANY(tags)`＋GINインデックスで足り、正規化が必要になる規模（語彙数百・リネーム頻発）は当面来ない |
| 検証 | API 層で「固定語彙外の値は400・6つ以上は400・重複は400」 | 語彙定数はフロントと backend で共有（1箇所の定数から双方が参照） |
| 公開面 | public/unlisted の投稿ではタグも表示する（`/api/public/**` のホワイトリストに `tags` を追加）。**表示のみでリンクにしない** | タグはコンテンツの一部（何の話か）であり秘匿情報を含まない固定語彙 |

**クリック可能化の解禁条件（実測で判定。先に決めておく）**: ①`visibility='public'` の投稿が **30件以上**、かつ ②最多タグの付与数が **10件以上**（SQL: `SELECT unnest(tags), COUNT(*) ... GROUP BY 1`）になった時点で、「チームページ内のタグ絞り込み」（サイト横断ではなくチーム内スコープ）の解禁をオーナーへ提案する。サイト横断のタグページはその後も別裁定（§3.2 の禁止解除はオーナーのみが行える）。閾値の意味: 8語すべてが空でないことを保証はしないが、「クリックした先が空」の確率が体験を壊さない水準まで下がる最小値として置いた。

## 4. データモデル（Prisma・純追加のみ）

ARCH §3 の原則「既存モデルは変更しない・migration は純追加(expand)」を維持する。**既存カラムの型変更・削除はゼロ**。

### 4.1 新規1テーブル: Entry（投稿）

モデル名は `Entry`。`Post`・`Article` は v1 凍結モデルがスキーマに残置されているため同名新設は不可能であり、再利用もしない（§6・ADR-015 案）。

```prisma
// ===== 共有2: 投稿（本SPEC §4。ADR-015案） =====

model Entry {
  id       Int     @id @default(autoincrement())
  title    String  @db.VarChar(120)
  bodyMd   String  @db.Text          // Markdown 自由記述（〜50,000字をAPI検証）
  template String? @db.VarChar(30)   // 作成時に選んだテンプレ "setting-card"|"reflection"|"gear-review"|null(白紙)
                                     // 挙動には影響しない計測用（§13.2 テンプレ経由率）。後から変更しない

  // --- タグ（§3.4。固定語彙8語・最大5つ・API層検証。表示のみ＝当面クリック不可） ---
  tags String[] @default([])         // v1 Tag/ArticleTag は再利用しない。GINインデックスはクリック可能化の解禁時に追加

  // --- 図鑑メタ（任意。テンプレ「セッティングカード」がUI上で入力を促す） ---
  boatTypeId Int?
  boatType   BoatType? @relation(fields: [boatTypeId], references: [id])
  windMin    Int?      // kt。両方入力時のみ有効（0 ≦ windMin ≦ windMax ≦ 60 をAPI検証）
  windMax    Int?

  // --- 可視性（§5）。"private"|"team"|"unlisted"|"public" ---
  // 下書きは private に統合、Qiitaの「限定共有記事」は unlisted に統合（同じ概念を2つの名前で持たない）。
  // String＋API層検証。enum化しない理由は ADR-007 と同一（将来 followers 追加時に migration 不要で可逆）。
  // ただし現時点で "followers" は不正値として400で拒否する（PRD裁定3「共有3までUIに出さない」をDB受け入れ値でも守る）
  visibility String @default("private")

  publicSlug      String?   @unique @db.VarChar(32) // unlisted/public時のみ発行。crypto.randomBytes(9)のbase64url12字（共有1と同一方式）。非公開化で破棄
  publishedAt     DateTime?                         // 外部公開（unlisted/public）した日時。取り消しでnull
  publicViewCount Int       @default(0)             // 非KPI。UI/API非表示・運用SQLのみ（PRD §5-7）

  // --- 所有文脈（§5.3）。投稿時に選ぶ「所属」。作成後の付け替え不可（裁定1） ---
  teamId   Int?                       // null = 個人として投稿
  team     Team?    @relation(fields: [teamId], references: [id])
  authorId Int
  author   User     @relation("EntryAuthor", fields: [authorId], references: [id])

  sessionId Int?                      // リプレイへのリンク（任意）
  session   Session? @relation(fields: [sessionId], references: [id], onDelete: SetNull)

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@index([teamId, visibility, createdAt])
  @@index([authorId, visibility, createdAt])
  @@index([boatTypeId, windMin, windMax])   // 図鑑フィルタ用
}
```

### 4.3 設計上の約束

1. **全ての新規フラグ・既定値は「非公開側」**（`visibility=private`・公開系フラグ false）。migration 適用の瞬間に何かが公開されることは構造的に起こらない（バックフィル不要の根拠でもある）
2. 図鑑メタ（boatTypeId/windMin/windMax）は**第一級カラム**。「艇種×風速でカードを引く」フィルタを Markdown 本文のパースや Json 内部検索でやらない（ARCH §3「gridJson内部をWHEREで検索しない」と同じガード）
3. `template` は作成時に固定される計測列であり、投稿の種別・挙動を規定しない（テンプレを選んで全部消しても、それはただの投稿）
4. 部内公開（`team`）の閲覧境界は Session と同じ「`teamId` の TeamMember か」。個人投稿（`teamId=null`）にチーム権限は一切及ばない
5. Session→Entry の逆参照リレーションは張る（リプレイ画面に添付投稿を出すため）が、公開ペイロードでは昇格済み同士のみリンクを露出する（§7.3）
6. `tags` は固定語彙の配列であり、タグの正規化テーブルは作らない（§3.4。v1 `Tag`/`ArticleTag` の凍結は継続）

### 4.4 新規テーブル2: Stock（ストック＝あとで読む。2026-08-02 裁定）

```prisma
// ===== 共有2: ストック（本SPEC §4.4・§7.5）。完全非公開・数は誰にも出さない =====

model Stock {
  id        Int      @id @default(autoincrement())
  createdAt DateTime @default(now())

  userId  Int
  user    User  @relation(fields: [userId], references: [id])
  entryId Int
  entry   Entry @relation(fields: [entryId], references: [id], onDelete: Cascade)

  @@unique([userId, entryId])   // 二重ストック防止（作成は冪等: 既存なら200で既存を返す）
  @@index([userId, createdAt])  // 「自分のストック一覧」専用。entryId 起点の index は意図的に張らない（「この記事を誰が/何人ストックしたか」を引くクエリは仕様上存在しない）
}
```

**設計上の約束（この機能の存在理由に関わるため、モデル定義と同格で明記する）**:

1. **ストックは完全に非公開である。** 他の部員にも、**その記事を書いた author 本人にも**見えない。理由: ストックが author に見えると**実質いいねになる**。10人規模では「誰がストックしたか」が特定でき、PRD §5 が恒久禁止する「いいね」と同じ力学——数や相手を意識して書く／ストックする——が裏口から入る。ストックは「読者の私的な付箋」であり、書き手へのシグナルではない
2. **ストック数をどのAPIにも出さない**（部内APIにも・author 本人向けにも・集計値としても）。UI の自制ではなく**API 層の出口で構造化する**。これは共有3 ADR-017 案の「フォロワー数を API に出さない」と同型の防波堤であり、禁止キーテスト（§11.2）の対象に「ストック数・ストック関係の値」を加える
3. Entry 削除時はストック行もカスケード削除（残っても指す先がなく、404 の山になるだけ）。**ストックした記事が非公開化された場合、行は残置**し、一覧では「読めなくなった」ことだけを示す（タイトル・本文は出さない＝閲覧時点の認可で評価。§7.5）

## 5. 所有文脈 × 可視性 — ライフサイクルとマトリクス

### 5.1 マトリクス（所有文脈 × 可視性）

○=選択可 / —=存在しない組み合わせ（API 400）

| visibility | チーム文脈（`teamId` あり） | 個人文脈（`teamId=null`） | 閲覧できる人 |
|---|---|---|---|
| `private` | ○（既定・下書き兼用） | ○（既定・下書き兼用） | **author 本人のみ**（チーム admin も見えない） |
| `team` | ○ | **—**（チームがないので部内という概念がない） | その `teamId` の TeamMember |
| `unlisted` | ○（昇格操作で到達） | ○ | URLを知っている全員（ログイン不要） |
| `public` | ○（昇格操作で到達） | ○ | 全員。チームページ／プロフィール一覧にも掲載 |
| `followers` | — | —（**共有3まで値ごと存在しない**） | — |

### 5.2 状態遷移

```
チーム文脈:  private ⇄ team ──(昇格・1方向操作)──▶ unlisted / public
                ▲                                        │ 取り消し（誤爆救済）
                └──── slug破棄して team へ戻る ◀───────────┘

個人文脈:    private ──(公開)──▶ unlisted / public
                ▲                      │ 非公開化
                └── slug破棄して private へ ◀┘

削除: どの状態からでも物理削除可（公開URLも即404）
```

- **private⇄team（部内側の遷移）は日常操作**。PRD の「1方向」制約は*チーム→外*にのみ適用される（PRD §5-2 の裁定どおり）
- **外向き（unlisted/public）への遷移と取り消しは、Session の昇格と完全に同型**: 昇格時に `publicSlug` 発行 → 取り消しで**スラッグ破棄** → 再公開は**新スラッグ**。個人文脈の public⇄private 切替にも同じルールを適用する（一度外に出たURLが中身だけ差し替わって生き続ける状態を作らない。共有1裁定を全公開物の統一契約にする）
- **編集**: 全状態で可（author 本人＋§5.3 裁定3 の範囲で admin）。**unlisted/public 状態での編集は確認ダイアログを挟む**（「この投稿は外部に公開されています」。共有1の R-05＝再同意と同型。判定は純関数に切り出しテスト対象＝M4-03 の教訓）
- **削除は物理削除**。ソフトデリートは全経路の `deletedAt` 条件漏れ1つが露出事故になるため S規模では採らない（復元需要が実証されたら再設計）

### 5.3 所有文脈の裁定4点（Qiita の Organization が実際に抱える問題。逃げずに裁定する）

**裁定1: チーム文脈⇔個人文脈の付け替えは不可（作成時確定）。**
`PATCH` で `teamId` は変更できない（400）。理由: ①チーム文脈投稿は部内に公開され、反省会の文脈で読まれ・リンクされた**チームの資産**であり、個人へ引き抜けると「部内で見えていた知見が author の都合で部から消える」経路になる（引き継ぎ＝プロダクトの原点と正面衝突）②逆方向（個人→チーム）を許すと、個人 `private` で書き溜めた本文が付け替え操作1つで部内に露出する事故面が増える。誤選択の救済は「削除して作り直し」（作成直後に気づく前提。本文コピーで実害は小さい）。付け替え需要が実測されたら「複製を作る」機能（原本は残る・非破壊）として再検討する。

**裁定2: 退部（TeamMember 削除）してもチーム文脈の投稿はチームに残る。author 表示もそのまま。**
理由: 「代替わりで消える部の知見を残す」が v1 からの原点（PRD §2）。退部＝知の消滅では本末転倒。実装上も User 行は消えない（`isActive` 運用）ため参照は壊れない。退部者は TeamMember 検証により**閲覧も編集も自然に失う**（追加実装不要が この裁定の利点でもある）。本人が退部前に自分の投稿を削除する自由は残る（author 権限）。匿名化オプションは作らない（YAGNI。要求が実在したら再裁定）。

**裁定3: チーム admin は、チーム文脈の投稿を（他人の作でも）編集・削除・可視性変更できる。ただし `private` は不可・個人文脈は一切不可。**
理由: チームページはチーム名で外部に出るため、掲載物への管理責任は admin に置く必要がある（退部者投稿の後始末・誤公開の取り消し・不適切内容の削除＝これが本設計のモデレーションの実体）。一方 `private` は「まだ誰にも見せていない下書き」であり、admin が覗ける設計は書くこと自体を萎縮させる。個人文脈はチームの管理範囲外。admin による編集は author 名を変えない（改変責任の透明化として、編集ダイアログに「他のメンバーの投稿です」を表示する）。

**裁定4: 編集履歴は持たない（`updatedAt` のみ）。**
Qiita には編集履歴があるが、あれは不特定多数の編集リクエスト・共同編集を前提にした装置。本プロダクトの書き手は当面部員10人＋author/admin しか編集できないため、履歴テーブル（全版保存＝容量・露出面・UI）のコストに見合わない。「公開後に大幅に書き変わった」ことへの外部読者の保護は、公開中編集の確認ダイアログ（§5.2）と `updatedAt` 表示で足りるとする。乱用が実測されたら再裁定。

## 7. API 設計

### 7.1 エラー形式・ページング・レート制限（横断規約）

- **エラー形式**: 既存踏襲 `{ error: string }`＋HTTPステータス。公開系は「存在しない/非公開/取り消し済み/未オプトイン」を**一律404**で区別しない（ADR-007・ADR-012 の思想を継承）
- **ページング**: カーソル方式 `?cursor=<id>&limit=20`（既定20・最大50）。応答は `{ items: [...], nextCursor: number | null }`。offset 方式にしない理由: 公開エンドポイントで大きな offset はDBを深くスキャンさせる攻撃面になる
- **レート制限**: `/api/public/**` は共有1と同じ IPあたり 60 req/min（メモリ内カウンタ・ADR-010 の信頼モデルに従う）。**書き込み系（投稿作成）は userId 単位 30回/時**（スパムの頭打ち。M4-01 の教訓＝「新しくDB行を作る書き込み口を素通しにしない」）

### 7.5 ストックの認可と非可視性（2026-08-02 裁定の執行部）

| 操作 | 本人 | 記事の author | 同チーム member / admin | それ以外 |
|---|---|---|---|---|
| ストックする／外す（`PUT`/`DELETE /api/entries/:id/stock`） | ○（**自分に閲覧権のある記事のみ**。閲覧権なしは404） | —（自分の記事も自分でストック可。ただし他者のストックは下記どおり見えない） | — | — |
| 自分のストック一覧（`GET /api/stocks/mine`） | ○ | × | × | × |
| **他人のストック（誰が・何を・何件）** | — | **×（API が存在しない）** | **×（同）** | **×（同）** |

- **「見せない」ではなく「引く経路が存在しない」で守る**: entryId 起点のストック取得APIを作らず（§4.4 の index 設計と対）、どのシリアライザにもストック集計を含めない。author 本人・チーム admin への例外も作らない
- ストック可否は**ストック時点＋閲覧時点の両方**で記事の閲覧権に従う（§7.4 のマトリクスをそのまま参照。ストック済みでも記事が private 化されれば一覧では `unavailable` になる＝ストックが閲覧権のバイパスにならない）
- ストック有無のフラグ（`isStockedByMe`）は**自分の文脈でのみ**部内APIの記事詳細に含めてよい（自分の付箋を自分が見るのは非公開性と矛盾しない）
- レート制限: ストック作成も userId 単位 30回/時（§7.1 の書き込み系と同枠。DB行を作る書き込み口を素通しにしない＝M4-01 の教訓）

### 8.1 ヘッダーメニュー（ログイン済み）の情報設計（2026-08-02 裁定）

機能を平坦に並べず、**3つの束**で構成する。**束を先に決める目的は、今後機能が増えても並びが崩れないこと**——新機能は「どの束に入るか」を答えてから追加する（答えられない機能はナビに載せない）。

```
[つくる]                      [じぶんの]                    ──────────（区切り）
  記事を書く（/posts/new）       自分の記事（/posts?filter=mine）   ハンドブック
  セッションを取り込む            ストック（/stocks）              設定
                                セッション一覧（/sessions）        ログアウト
```

| 束 | 意味 | 将来の機能が入る場所 |
|---|---|---|
| **つくる** | 何かを新しく生み出す行為の入口 | （共有3以降も増やさない方針。作る行為は記事とセッションの2本に集約） |
| **じぶんの** | 自分に紐づくものの一覧 | **フォロー（/feed・共有3）はここ**（「自分が購読しているもの」＝自分に紐づく受信面）。自分のチームの部内ページもここ |
| **全体**（区切りの後） | 個人に紐づかないサイト全体のもの | ハンドブック・設定・ログアウト。**チーム公開ページの管理（オプトイン・publicBio）は「設定」配下**（チーム設定の一部であり、ナビの第一階層に出さない） |

**既存コンポーネントとの関係・整合**:

- **`TopBar`（デスクトップ）**: この3束をそのままドロップダウン／ナビ項目のグルーピングに使う。束の順序は「つくる → じぶんの → 区切り → 全体」（書く行為を最前に置く＝供給第一の製品方針をナビの並びで表現する）
- **`BottomTabBar`（モバイル）**: タブ数の物理上限があるため3束をそのまま展開せず、**各束の代表1つ**（つくる=＋ボタン／じぶんの=セッション一覧／全体=メニュー）に畳む。「メニュー」タブの中の並びは本節の3束に従う。束が正であり、タブは束の射影——という主従を固定する
- **`/p/`（公開ビュー）で出さない原則（T-33）との整合**: 本節のヘッダーメニューは**ログイン済みの部内面専用**。公開ビュー（`/p/`・`/teams/[slug]`・`/posts/p/`・`/sailors/`）には従来どおりログインナビ・タブバーを一切出さない（公開面は読むだけ・登録導線を強制しない＝共有1の契約）。本裁定は T-33 を変更しない（XSS 防波堤。ARCH §5「dangerouslySetInnerHTML 禁止」の適用）**:

1. レンダラは **React 要素として出力する方式**（例: react-markdown 系）とし、HTML 文字列を組み立てて `dangerouslySetInnerHTML` に流す方式は禁止
2. **raw HTML は無効のまま使う**（rehype-raw 等の HTML 解禁プラグインを入れない）。`<script>` どころか `<iframe>`・`<img onerror>` を含む本文も、ただのテキストとして描画される
3. 画像は Markdown 構文（外部URL）のみ許可。`loading="lazy"`・`referrerPolicy="no-referrer"` を付与（外部サーバへ閲覧者情報を渡さない）
4. リンクは `rel="noopener noreferrer nofollow"`（公開面がスパムリンクの置き場にされる誘因を消す）
5. **新規 npm 依存 1〜2 件（レンダラ本体＋GFMプラグイン程度）が必要 = Team Lead 承認制**（AGENTS 制約1・実装ルール6）。ARCH §1 で温存してきた「新技術予算・プロジェクトあたり1つ」を**共有2で消費する**宣言であり、選定・承認は SH2-02 着手時に行う（部内向けと公開向けで同一レンダラ・同一設定を使い、二重化しない）

## 9. 秘匿境界の段階変化 — M4-02 の裁定と ADR 起票案（ARCH.md への提案）

> **本節が Issue #5 の追加裁定依頼への回答。** ARCH.md への実際の追記は Team Lead が行う（本書は文面の提案まで）。

### 9.1 裁定の要旨

1. **共有2以降、team slug は「公開ページを有効化（オプトイン）したチーム」については公開情報として扱う**。全チーム一律の公開はしない。反省会ツールとしてだけ使うチームの秘匿は従来レベルのまま維持される
2. **未オプトインチームについても、「存在の完全秘匿」は保証文言から降ろす**。M4-02 が示すとおり `POST /api/teams` の 409 応答で slug の存在有無は観測可能であり、slug がユーザー入力の人間可読文字列である限り、作成時の衝突通知は仕様上不可避（衝突を教えなければ作成UXが壊れる）。守るべき実体は「存在の有無」ではなく**「中身（招待コード・名簿・非公開セッション・非公開投稿・活動実態）」**であり、これらは招待コード（128bit）・TeamMember 検証・オプトインで守られている。共有1段階の対応は REVIEW-4 M4-02 推奨の **①受容＋ADR訂正 と ②M4-01 のレート制限 の併用**を支持する
3. **ADR-013 帰結欄の「コードを知らない者はチームの存在すら観測できない」は実態と食い違っているため訂正する**（訂正文面は §9.3）
4. **秘匿レベルは段階×チーム設定で変わることを明文化する**（下表。ADR-014 案に収録）

**秘匿レベル対応表（ADR-014 案に含める正本）**:

| 情報 | 共有1（現在） | 共有2・未オプトイン | 共有2・オプトイン済み |
|---|---|---|---|
| team slug の存在有無 | △ 409経由で観測可（受容・レート制限で緩和） | △ 同左 | **公開**（URLそのもの） |
| チーム名・大学・公開bio | 秘匿（メンバーのみ） | 秘匿 | **公開** |
| 部内bio（`Team.bio`）・部内メモ | 秘匿 | 秘匿 | **秘匿のまま**（公開は別カラム `publicBio`） |

### 9.2 ADR-014 案（新規追記の提案文面）

> ### ADR-014: チーム公開ページはオプトイン制とし、秘匿保証を「存在の秘匿」から「中身の秘匿」へ再定義する（ADR-013 帰結欄の訂正を含む）
> - **状況:** REVIEW-4 M4-02 — `POST /api/teams` の 409 が team slug の存在オラクルになっており、ADR-013 帰結欄「コードを知らない者はチームの存在すら観測できない」が成立していない。同時に、共有2（SPEC-share2-team-pages.md）はチーム公開ページを作るため、slug の秘匿前提そのものが段階で変わる
> - **決定:** ①チーム公開ページは `Team.isPublicPageEnabled`（既定 false）の **admin オプトイン制**。未オプトインチームへの公開経路は一切増えない（`GET /api/public/teams/:slug` も一律404） ②秘匿の保証対象を「存在の有無」から「中身（招待コード・名簿・非公開コンテンツ）」へ再定義する。slug 存在有無の 409 観測は**受容**し、M4-01 のレート制限で辞書攻撃コストを上げる ③秘匿レベルの段階対応表（SPEC-share2 §9.1）を正本とする ④公開ページのメンバー掲載は**部員本人の同意**（`TeamMember.showOnPublicPage`、既定 false）を必須とし、admin による代行掲載は許さない
> - **却下した代替案:** (a) slug をサーバ生成にして存在オラクルを消す — 公開ページURLの可読性（新歓ビラに書ける）と衝突し、S規模に過剰（REVIEW-4 M4-02 案③の評価どおり） (b) 全チーム自動公開 — 反省会ツールとして使うだけのチームの期待を裏切る。既定を公開側に倒す変更はオーナー裁定なしにできない (c) 409 を汎用 400 にぼかす — 成功/失敗の差から存在は推定でき、UXを壊す割に秘匿は改善しない
> - **選ばなかった側の最強の擁護論:** 「オプトインは設定項目を増やす。公開ページが共有2の目玉なら全チーム公開が単純」— 単純さの利点は認める。ただし現ユーザー（自部）が同意した公開範囲は「昇格したコンテンツ」だけであり、チームの存在・名簿の公開に同意した事実はない。既定を公開側に倒す失敗は取り返しがつかない種類（一度クロールされた情報は消えない）である、が反駁
> - **結果として受け入れるデメリット:** 「slug の存在有無は隠せない」という割り切りが恒久化する。チーム設定UIが1画面増える。ADR-013 帰結欄の保証文言を弱める方向の訂正になる（ただし実態に文書を合わせる訂正であり、実装を文書に合わせて弱めるのではない）

### 9.4 ADR-015 案（投稿モデルの選定）

> ### ADR-015: 投稿は単一 Entry モデル（Markdown 本文＋任意の図鑑メタ＋テンプレ由来記録）で実装し、v1 の Article / Post を再利用しない
> - **状況:** 共有2の投稿のデータモデル選定。オーナー裁定（2026-08-01）により「自由記述を基本、テンプレは下書きの出発点」（Qiita型）。候補: (a) v1 `Article` 再利用 (b) v1 `Post` 再利用 (c) テンプレ種別ごとの構造化専用テーブル（SettingCard/Reflection の2本） (d) 単一 `Entry` テーブル＋Markdown本文＋任意メタ
> - **決定:** (d)。本文は `bodyMd`（Markdown）、図鑑の検索軸（boatTypeId/windMin/windMax）だけを第一級の任意カラムに持ち、テンプレは DB ではなくフロントの雛形定数とする。どのテンプレ経由で作られたかは `template` 列に記録する（挙動に影響しない計測列＝供給検証用）
> - **理由:** テンプレが「出発点であって強制ではない」以上、フィールド構造をスキーマで固定する (c) は裁定と両立しない（雛形を消した瞬間に型が破綻する）。(a) Article は可視性モデルが別物（`isPublished` Boolean）で、Like/Comment/Tag と癒着しており、410凍結資産の復活は PRD rev.5 のアーカイブ削除裁定と逆行する。(b) Post は 300字短文で別物（削除方針維持＝ADR-005）。検索が必要な軸だけを列に昇格させ、本文は不透明な Text として扱う構図は、ARCH §3「gridJson の中を SQL で検索しない」と同じ整理
> - **選ばなかった側の最強の擁護論（(c) 構造化2テーブル）:** 「セッティングカードの価値は『艇種×風速×設定値で機械可読に引ける』ことにある。自由 Markdown に溶かすと設定値の構造が失われ、将来『全国の470の12ktセッティング比較』のような図鑑機能が作れなくなる」— 正当であり、実際 architect も裁定前は (c) を推していた。ただし①強制フォームは「書くことが決まっている」利点と引き換えに『型に合わない知見は書けない』摩擦を作り、部員10人の供給をさらに絞る ②図鑑の最重要軸（艇種・風速）はメタ列として残しており、設定値本体の構造化は「比較機能の需要が実測されてから」列を足せば移行できる（本文からの再入力は必要だが、その時点の投稿数は少ない見込み）③最終判断はオーナーの製品裁定に帰属する、が反駁
> - **結果として受け入れるデメリット:** 設定値の機械可読性を当面放棄する（図鑑は「絞り込んで人が読む」まで）。Markdown レンダラの新規依存（Team Lead 承認制・新技術予算の消費）。自由記述の解禁により PRD §5 の改訂が必要（SPEC-share2 §10 の提案文面・改訂実施は product-lead/Team Lead）

## 13. リスク・自己反論・失敗の早期検知

### 13.1 本設計への最強の反論 — 「共有2まで作っても、自部以外の供給は発生しない可能性が高い」

PRD §7 第5リスクが明記するとおり、**共有2止まり（自部のショーケース＋公開アーカイブで終わる）可能性は高い**。さらに本裁定（自由記述解禁）は v1 の死因と同じ形の器を作る決断であり、「テンプレが出発点にある」ことがどれだけ供給を救うかは**自プロダクトでは未検証**（アングラーズ/YAMAP は前例であって証明ではない＝PRD-rev4 §4-2 の自己反論のまま）。加えて、**本書を今書くこと自体の ROE も疑わしい** — 着手条件の達成は最短2ヶ月先で、その間の共有1運用実測（昇格の実利用・公開URLの実反応）次第で前提が変わる。設計は在庫であり、在庫は腐る。

これへの答え: ①中核裁定（オプトイン制・秘匿段階表・単一Entryモデル・所有文脈の4裁定・v1資産不使用）は運用実測に依存しない**構造の決定**で腐りにくく、実測依存部分（テンプレ雛形の中身・フィルタ軸・タブ構成）は薄く書いた ②M4-02 裁定は共有2と独立に**今**必要だった（ADR-013 が現に事実と食い違っている）③失敗は §13.2 の計測で早期検知し、「作ったのに動かない」を放置しない。それでも「着手時に3割は書き直す」見込みは正直に残す（§13.3 のチェックリストがその再検証手続き）。

### 13.2 失敗の早期検知（計測の定義。PRD §6 と整合）

**判定時点: 共有2リリース後 8週**（Phase 1 の計測期間と同じ長さ。観測は既存方針どおり SQL のみ・ダッシュボードは作らない）。

| # | 計測 | 閾値 | 観測方法（SQL） |
|---|---|---|---|
| K1 | 投稿者数（**オーナー以外**） | 2人以上 | `SELECT COUNT(DISTINCT "authorId") FROM "Entry" WHERE "authorId" <> <owner>` |
| K2 | 投稿ペース | 月4件以上（PRD §6 の共有2→3条件「構造化投稿月4件以上」と同一値） | `Entry` の月次 COUNT |
| K3 | テンプレ経由率 | 記録のみ（閾値なし）。`template` 列の分布で「テンプレが供給を救う」仮説自体を検証 | `GROUP BY template` |
| K4 | 自部以外からの投稿 | 発生の有無（共有3着手条件。8週時点では未発生を想定内とする） | teamId・author の所属で判別 |

**未達時のアクション（先に決めておく）**: K1 または K2 が8週時点で未達なら「**共有2は機能していない**」と判定し、①共有3着手の凍結（PRD §6 のゲートどおり）②原因の聞き取り（書く時間がない／価値を感じない／テンプレが合わない）③テンプレ改訂 or 公開面の宣伝停止（部内ツール＋昇格アーカイブとして維持＝PRD §7 第5リスクの終着点）を**オーナーへの再判定材料として提出**する。閲覧数・フォロワー的数値はここでも使わない（非KPI原則）。

### 13.4 本改訂（2026-08-02・6裁定）への自己反論 — 「1日で6件も裁定が入った。実装前の設計が肥大していないか」

正面から認めるべき事実: 着手条件が実測ゼロのまま、本書は1日でテンプレ1種・タグ・ストック（新テーブル1本）・ヘッダー情報設計を積み増した。見積も5.5日→6.5日に増えた。「実装が始まる前に仕様が育ち続ける」のは v1 の機能寄せ集めと同じ病型に見えるし、設計在庫が増えるほど着手時の書き直し面積（§13.1 の「3割は書き直す」）も増える。

これへの答え:

1. **6件の過半は「増築」ではなく「未決の穴埋め」である。** 公開範囲UI（§2.5）は既決の4値の見せ方の確定、メンバー欄（§2.3）は §15 論点4 として本書自身が裁定待ちに積んでいた項目、ヘッダー3束（§8.1)は既存画面が増えた時点でいずれ必要だった情報設計。純粋な機能追加はタグ・テンプレ3種目・ストックの3件で、うちタグとテンプレは**列1本と定数の追加**にとどめた（オーナー自身が「設計変更はほぼゼロ」を条件に裁定している）
2. **各件に「作らない側の防波堤」を同時に増設した。** タグは「辿れない」段階に固定し解禁条件を数値化（§3.4）、道具レビューは §3.2 の禁止を3項目増やし、ストックは「いいねの裏口」化を API 層で構造的に塞いだ（§4.4）。裁定6件のうち3件は実質「作らないことの決定」を含む
3. **それでも残るリスクは削る順序で受ける**: 追加分（ストック・ヘッダー3束・テンプレ3種目）はすべて §12 の削る順序に入っており、供給の縦1本（書く→昇格→チームページ）はこの改訂で1ミリも太っていない
4. ただし**次も同じペースで裁定が積まれるなら、それは Team Lead が止めるべきシグナル**である: 本書の DoD は「implementer が迷わず着手できる」ことであり、着手前の仕様書に対する改訂要求が月あたり数件を超えて続く場合、「設計を先に完成させる」方針自体（着手条件ゲートの位置）を Architecture Gate で再審すべきと申し送る

## 14. 新しく登場する概念・技術（初出の用語説明）

| 用語 | 説明 |
|---|---|
| **オプトイン（opt-in）** | 「本人が明示的に選んだ場合のみ有効化する」方式。逆はオプトアウト（既定で有効）。個人情報や公開範囲では**既定を安全側（非公開）に置くオプトインが定石**。本書ではチーム公開ページ・メンバー掲載・個人プロフィールの3箇所に適用。**応用**: メール配信同意・cookie 同意など規約系の設計全般で同じ判断軸が使える |
| **存在オラクル（existence oracle）** | システムの応答差分から「その資源が存在するか」を第三者が判定できてしまう経路（oracle=神託）。404/403 の使い分け・409 衝突通知・応答時間差が典型。本書では「秘匿すべきは存在か中身か」を切り分け、守れないもの（slug 存在有無）を明示的に受容した。**応用**: ログイン画面の「メールアドレスが存在しません」も同型の漏洩 |
| **テンプレート出発点方式** | フォームのフィールドを強制する（構造化入力）のではなく、自由記述エディタの**下書きに雛形テキストを差し込む**方式。Qiita のテンプレート機能と同じ。強制がないぶん供給の摩擦が低い代わりに、データの機械可読性は失う（このトレードオフの裁定が ADR-015 案） |
| **raw HTML 無効の Markdown レンダリング** | Markdown 中に書かれた生の HTML（`<script>` 等）を**解釈せずテキストとして表示する**設定。ユーザー投稿を表示する場では XSS（他人のブラウザで悪意あるスクリプトを実行させる攻撃）対策の第一防壁になる。**応用**: コメント欄・チャット・プロフィール自由記述など「他人が書いた文字列を描画する」あらゆる場面で同じ判断が要る |
| **カーソルページング** | 「前ページ最後の id より後を limit 件」という取り方。offset 方式（`?page=3`）と違い途中挿入でズレず、大きなページ番号で DB を深くスキャンさせる攻撃面もない。**応用**: 時系列一覧を持つ API ほぼ全てで第一候補 |
| **expand / contract** | migration を「追加だけの段階（expand）」と「削除の段階（contract）」に分ける定石（ARCH ADR-003 で採用済み）。本書の migration は expand のみで、rollback が DROP だけで済む |
