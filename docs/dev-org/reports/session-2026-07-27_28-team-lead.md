## 2. 見つけた重大な欠陥（すべて Team Lead が実測で再現）

### 2.1 未認証で部員名簿が取得できた（Blocker R-01 → B-02）

公開ページにチーム名を出したことで「チーム名 → チーム詳細API → **部員の氏名・専門・経験年数**」と辿れる経路が成立していた。

**Team Lead は一度これを「解消した」と誤報告している。** 未認証の401しか確認せず、「登録した部外者」を試していなかった。第2次監査がそこを突き、実際に再現できた。`POST /api/auth/register` は招待コードもメール確認も承認もなくJWTを返すため、**「認証済み」と「部外者でない」は同値ではなかった**。

修正は「認可を強くする」ではなく **「機密境界を定義し直す」** 方向で行い、関係を定義できない機能（`sailors` / `users/:username` / `teams/:slug/{articles,questions}`）は410で凍結した（ADR-012）。

### 2.2 テスト実行が本番DBを破壊し得た（Blocker B-01）

`export DATABASE_URL=<本番>` した状態で `npm test` を叩くと、`dotenv` がシェルの既存環境変数を上書きしないため `.env.test` が効かず、**本番が全テーブル TRUNCATE** される状態だった。マイグレーションをローカルから流す案内をした直後で、現実的な危険だった。

さらに深掘りで、**`.env.test` はこれまで一度も効いていなかった**ことも判明した。`docker compose exec backend npx jest` はコンテナの `DATABASE_URL`（＝**開発DB**）を使っており、Team Lead が何度も報告した「83 passed」は毎回**開発DBを消しながら**走っていた。

### 2.3 レート制限が反省会当日に全員を締め出す設計だった（Blocker B3-01）

login のレート制限がIP単位（60秒10回）だった。**部室の共有Wi-Fi・大学NATは全員が同一グローバルIP**なので、11人目から60秒間ログイン不能。この製品の唯一の利用シーン（部室に集まって全員でログイン）と正面から衝突していた。

しかもプロジェクトは**同じ罠を一度踏んで公開APIでは解決済み**で、`public.ts` にコメントまで残っていた。教訓が適用されていなかった。

修正は「キーをIPからemail中心へ変更」「成功したログインはカウントしない」「IP単位は緩めてDoSの蓋としてのみ残す」。**総当たり防止の本質は「1アカウントへの試行回数」であって「そのIPからの回数」ではない**、という筋の通し方。

### 2.4 flakyテストの真因（supertest の一時サーバ生成レース）

`supertest` の `request(app)` は**呼び出しのたびに `http.createServer(app)` して `listen(0)`、応答後に `close()`** する。これが密集するとレースが起き、**リクエストがルートハンドラに到達しないまま404が返る**。

決定打は `t31` に仕込んだデバッグログ。**61回リクエストしたのにハンドラ内のログが60回しか出ない**。読解では到達できず、計測でしか取れない結論だった。

これにより、バラバラに見えていた症状が1つの原因で説明できた。

| 症状 | 説明 |
|---|---|
| 401期待→404 / 400期待→404 / 403期待→404 | ハンドラ未到達 |
| 落ちる場所がランダム | どのリクエストがレースを踏むかは運 |
| 単独ファイルでは再現しにくい | 生成・破棄の密度が下がる |

対策は共通ヘルパー `helpers/testServer.ts` を新設し**12ファイル全てを移行**。**Team Lead が単独実行で10回連続 133 passed / 0 failed を実測**。

## 4. 事故と、そこから作った防波堤

| 事故 | 対処 |
|---|---|
| **並行セッションとのマージ競合**（別セッションが §7 と T-20 を二重実装） | オーナー裁定でローカル優先解決。ブランチ体制（trunk＋claude/＋codex/）を整備 |

| **エージェントが検証ループで停止（5名）** | 分担を変更: 実装担当はフルスイート最大2回、10回連続検証は Team Lead |
