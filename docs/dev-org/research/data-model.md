### RQ-03 の所見（推奨まで。決定ではない — 決定は architect）

- 独立ソースの一致状況: **分かれている** — LeafletPlaybackは「事前グリッド化」方式、deck.gl TripsLayerは「生タイムスタンプ＋実行時補間」方式で、いずれも実運用ライブラリだが採用方式が逆。ただし両者とも「二分探索を明示的に使う」実装は確認できなかった（deck.glはGPU側処理で二分探索に相当する概念自体がない）。打ち切り理由: 上限5件のうち2件で明確に分岐したため、3件目（sailing特化のmkobetic/gpx）も見たが実装詳細非公開で判定材料にならず、これ以上の追加ソースでも「どちらが優れているか」の決着は付きにくいと判断し打ち切り
- 補足: RQ-03はRESEARCH.md記載の通りSPIKE-01（性能検証）が本命の判定材料。本メモは「事前グリッド化は実装例がある・破綻しない設計」という安心材料と、「生タイムスタンプ方式も主要ライブラリで採用例がある」という選択肢の実在性を示すに留まる
- 反証探索の結果: 「事前グリッド化は情報量を落とす（実測値との誤差が生じる、欠測を無理に補間で埋めると議論を誤誘導するリスク）」という直接の反証記事は見つからなかった（検索語: "GPS resampling data loss accuracy concern race analysis"）。ただしLeafletPlayback自体のIssue/Discussionsは未読（打ち切り条件の上限内で優先度を下げた）

### RQ-05 の所見（推奨まで。決定ではない — 決定は architect）

- 独立ソースの一致状況: **一致**（TOAST発動閾値と劣化傾向について、PostgreSQL公式Doc・evanjones実測ブログ・ScaleGridブログの独立3ソースが同じ結論＝「2KB超でTOAST化し性能劣化リスクがある」を支持）。ただし「本プロジェクトのアクセスパターン（1レコード全件フェッチ・書き込みは取込時1回のみ）でその劣化がどこまで効くか」は、いずれのソースも直接検証しておらず**確証なし**。打ち切り理由: 上限5件到達（TOAST一般論は独立2ソース一致で打ち切り可能だが、「本プロジェクトの用途に当てはまるか」という一段深い問いは未解決のまま情報源を使い切った）
- 反証探索の結果: 「時系列GPSデータはJSONB配列でなく正規化行（1fix=1行）で持つべき」という反証寄りの主張を発見（検索語: "postgres time series GPS points store as rows vs JSONB array anti-pattern"）。要旨:「正規化テーブルなら`timestamp`+`series_id`+`value`のインデックスで集計クエリを高速最適化できるが、配列/JSONBは値ごとの統計がなくシーケンシャルスキャンになりやすい」。ただしこの反証は「時刻範囲での集計・複数艇横断クエリを頻繁に行う」用途を前提にしており、本プロジェクトの主用途（1練習分をまるごと読んで再生する）とは前提が異なる。**この前提の違いこそがRQ-05(a)と(b)の分岐点**であり、architectの判断材料として明記する

### RQ-06 の所見（推奨まで。決定ではない — 決定は architect）

- 独立ソースの一致状況: **一致**（GPX 1.1仕様が定義する必須/任意フィールドはtrkpt+time+ele程度とシンプルであること、かつ主要OSSパーサ2つ（GPXParser.js系列）がどちらもこの範囲を軽量に処理できることで一致）。DOMParserは全ブラウザ標準APIであり依存追加なしで完結できる。打ち切り理由: 独立2ソース一致（公式仕様のシンプルさ＋OSS実装の軽量さ）
- 反証探索の結果: 「自前DOMParserの手書き文字列処理は遅い」という指摘を検索で見たが（検索語: "gpxjs vs gpxparser benchmark large file performance issue github"）、これは「ブラウザ標準の`DOMParser` APIでなく正規表現等で自作パースする場合」の話であり、`DOMParser`を使う前提のRQ-06(a)には当てはまらない。したがって直接の反証は見つからなかった

### RQ-09 の所見（推奨まで。決定ではない — 決定は architect）

- 独立ソースの一致状況: **一致寄りだが確証は弱い** — 動画注釈OSS実装（一次ソース確認済み）は「時刻必須＋対象/位置は任意フィールド」という設計を裏付けるが、もう1件（Hudl系）は一次ソース未確認の二次情報に留まる。RQ-09はミッション上「2ソースで十分」と指定されているため、精度に留保をつけた上で打ち切り
- 反証探索の結果: 「注釈に対象艇・レグを必須にすると入力コストが上がり書き込み率が落ちる」という懸念に直接言及する一次ソースは見つからなかった（検索語: "annotation required fields reduce user contribution rate UX"）。ただしPRD自体がRQ-09(a)候補（最小構成）を挙げている通り、この懸念はプロジェクト内で既に認識済み

### RQ-10 の所見（推奨まで。決定ではない — 決定は architect）
