## 1. 指摘一覧（Team Lead 検証済み）

### C-01 `boatLabel` が自由入力のまま未認証の公開レスポンスに出る — **確認**

- **場所**: `backend/src/lib/serializePublicSession.ts:56`
- **事象**: 公開ページのレスポンスに `boatLabel` がそのまま載る。ユーザーが「田中艇」のように実名を入れていた場合、
  未認証の第三者に部員の氏名が露出する。
- **検証**: 確認。`tracks.map` に `boatLabel: t.boatLabel` があり、フィルタ・マスクは無い。
  ホワイトリスト方式自体は守られている（他の内部カラムは出ていない）が、**ホワイトリストに載っているカラムの中身が
  自由入力**である点が抜けている。
- **判定**: 実在する。ただしこれは**コードのバグではなく設計の穴**であり、修正は「公開ダイアログで boatLabel を
  確認・編集させる」か「公開時に別名を付けさせる」かの**プロダクト判断**が要る。
- **深刻度**: Medium（同意）

### C-02 脱退・除名後も本人が注釈を更新・削除できる — **確認**

- **場所**: `backend/src/middleware/requireTeamMember.ts:79`（`isAuthorOrTeamAdmin`）
- **事象**: `if (authorId === userId) return true;` で即座に許可し、TeamMember であることを確認しない。
- **検証**: 確認。呼び出し側 `backend/src/routes/annotations.ts:12,46` の PATCH / DELETE は
  ミドルウェアが `authMiddleware` のみで、チーム所属チェックが**経路上どこにも無い**。
  除名された元部員が自分の注釈を後から書き換え・削除できる。
- **影響範囲の限定**: 書き換えられるのは**自分が書いた注釈だけ**。他人の注釈・セッション・トラックには到達しない。
- **深刻度**: Medium（やや過大。実害は「退部者が自分の発言を消せる」まで。ただしチームの記録の一貫性は損なわれる）

### C-03 async 認可ミドルウェアが `wrap()` の外にある — **確認。ただし帰結の説明が要修正**

- **場所（Codex の指摘）**: `backend/src/middleware/requireTeamMember.ts:27`
- **実際の欠陥箇所**: `backend/src/routes/sessions.ts:39` — `requireTeamMemberByBody()` を `wrap()` せずに渡している。
  ミドルウェアの定義側ではなく**マウント側**が問題。
- **検証**: 確認。Express 4 は async ミドルウェアの reject を捕捉しないため、`prisma.teamMember.findUnique` が
  投げるとハンドラチェーンが止まる。
- **帰結の訂正**: Codex は「500応答へ収束せず未処理rejectionになる」としたが、`backend/src/index.ts:93,96` に
  `unhandledRejection` / `uncaughtException` のプロセスレベルハンドラが**意図的に**置かれている（コメントに
  「多重防御」と明記）。したがって**プロセスは落ちない**。実際に起きるのは
  **そのリクエストだけが応答を返さずクライアントのタイムアウトまでハングする**こと。
- **発生条件**: DB 障害時のみ。平常時には起きない。
- **深刻度**: Medium → **Low 相当**（多重防御が効いており、最悪ケースは既に潰されている）

### C-04 `startSec` と点 index の丸め基準が異なり、艇間同期が最大1秒ずれ得る — **確認。実質これが一番効く**

- **場所**: `frontend/src/lib/gpx/parse.ts:107,115`
- **事象**: 二重丸めになっている。
  - `startSec = Math.round((t0 - sessionStartMs) / 1000)` … 艇の開始位置を丸める
  - `relSec = Math.round((p.timeMs - t0) / 1000)` … 各点を **t0 基準で**丸める

  グリッド上の点 i の絶対時刻は `sessionStartMs + (startSec + i) * 1000` として扱われるが、真の時刻は
  `t0 + relSec * 1000`。丸めが2回入るため誤差が加算され、**最大で約1秒**の艇間ずれが出る。
  各艇の GPS が異なる小数秒位相で記録していると顕在化する（まさに実運用の条件）。
- **検証**: 確認。コードを読んだ上での論理的帰結であり、実データでの実測は未実施（**未検証**）。
- **修正方針**: 各点を **`sessionStartMs` 基準で1回だけ丸める**（`Math.round((p.timeMs - sessionStartMs)/1000)`）
  ようにすれば丸めが1回になり、誤差は最大0.5秒に半減し、かつ艇間で基準が揃う。変更は局所的。
- **既存Issueとの関係**: Issue #30（艇ごとの記録開始時刻のズレを取込時に表示する）と**別問題**。
  #30 は「そもそも押した時刻が違う」という物理のズレ、C-04 は「同じデータでも実装が入れるズレ」。
  **C-04 は実装で消せるので先に消すべき。**
- **深刻度**: Medium（同意。反省会リプレイの中核価値＝艇の比較に直接効く）

### C-05 複数艇アップロードの途中失敗で、Session と先行 Track だけが残る — **確認**

- **場所**: `frontend/src/app/sessions/new/page.tsx:131-146`
- **事象**: `POST /api/sessions` でセッションを作った後、`for (const g of normalized.grids)` で Track を
  1本ずつ POST する。2本目が失敗すると catch に飛び、**セッションと1本目のトラックだけが DB に残る**。
  ユーザーは画面遷移せずエラーを見るが、DB には中途半端なセッションが生まれている。
- **検証**: 確認。ロールバック処理も、再送時の重複防止も無い。
- **深刻度**: Medium（同意。6艇アップロードで途中失敗すると、ゴミセッションが積み上がる）

### C-06 admin 数チェックと降格が非トランザクション — **確認**

- **場所**: `backend/src/routes/teams.ts:351-357`
- **事象**: `prisma.teamMember.count(...)` で admin 数を数えてから `prisma.teamMember.update(...)` で降格する。
  この間にトランザクションが無い。admin が2人のとき、2つの降格リクエストが同時に来ると**両方が
  `adminCount <= 1` のチェックを通過**し、admin が0人のチームが残る。
- **検証**: 確認。read-then-write レースであり、`prisma.$transaction` で囲めば塞げる。
- **補足**: この 409 チェック自体は 2026-07-30 に Team Lead が「ADR未規定だが目的から演繹できる」として
  追加したもの（コード内コメントに経緯あり）。**守ろうとした不変条件が並行時には守れていない**という指摘。
- **発生条件**: 管理者2人が同時に降格操作をする、という稀な同時実行。
- **深刻度**: Medium → **Low 相当**（実運用での発生確率は低い。ただし復旧経路が無い＝起きたら詰むので、
  修正コスト（`$transaction` で囲むだけ）に対して見合う）
